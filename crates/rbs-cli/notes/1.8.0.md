# rbs 1.8.0

## Le module qui instancie le client d'API change de fragment propriétaire

`frontend/src/api/index.ts` était déposé par `frontend-admin` ; il l'est désormais par
`frontend`. Rien ne bouge sur votre disque : une publication n'écrit chez personne, et
votre projet garde le fichier que son installation lui avait écrit. Ce qui change est ce
qu'une installation neuve produit, et ce que `rbs remove frontend-admin` emporte — le
retrait laisse maintenant ce module en place, comme il laisse déjà le routeur du socle.

Le contenu n'est plus tout à fait le même. Le socle parle à son API sans jeton ; le shell
d'administration ajoute l'en-tête d'autorisation par un module à lui,
`frontend/src/api/entetes.ts`, que `src/api/index.ts` découvre comme le routeur découvre un
montage. Sur un projet qui porte les deux fragments, le comportement est identique : la
même instance, le même en-tête, les mêmes appels.

Si vous voulez aligner un projet existant sur cette disposition, il n'y a rien à
désinstaller : recopiez les deux fichiers depuis un projet neuf, ou laissez le vôtre tel
quel — il continue de fonctionner.

## `rbs generate client` écrit là où le frontend le lira

Sans `--out`, la commande écrivait toujours dans `clients/ts/client.ts`. Sur un projet qui
porte le fragment `frontend`, elle écrit désormais dans `frontend/src/api/client.ts` : hors
de l'arbre du client, le serveur de développement ne voyait rien de ce qu'elle produisait.

**Sur un projet sans frontend, rien ne change.** Si vous portez le frontend et que vous
aviez un `clients/ts/client.ts`, la prochaine régénération sans `--out` en écrira un second
à l'autre endroit plutôt que de mettre le premier à jour : passez `--out clients/ts` pour
garder l'ancien, ou supprimez-le.

## Le thème sombre existe, et s'allume tout seul

La variante sombre était accrochée à une classe que seul le magasin d'interface du shell
d'administration posait, et le bloc de thème n'avait qu'un jeu de valeurs : sur un projet à
socle seul, la moitié de la charte était du code mort.

`frontend/src/assets/main.css` porte maintenant un second jeu de valeurs, et
`frontend/src/lib/theme.ts` — un fichier neuf du socle — pose la classe au démarrage, à
partir du choix retenu ou, à défaut, de la préférence du système. Un projet existant ne
reçoit rien tant qu'il ne réinstalle pas le fragment ; une installation neuve démarre en
sombre sur une machine réglée en sombre.
