# rbs 1.3.0

## `rbs add` range ses modules sous `src/modules/`

Dix fragments écrivaient jusqu'ici à la racine de `src/`, mêlés aux features que vous
engendrez vous-même : `audit`, `cache` (le répertoire qu'écrit `redis`), `cors`, `jobs`,
`mail`, `observability`, `rate_limit` (ce qu'écrit `rate-limit`), `scheduler`, `storage`
et `webhooks`. Ils s'installent désormais sous `src/modules/`, dont le point de montage
est `src/modules/mod.rs` — ouvert au premier fragment qui en a besoin, puis retrouvé par
l'ancre `<rbs:modules>` à chaque suivant. C'est la quatorzième ancre, aux côtés des treize
que le CLI connaissait déjà.

`auth` fait exception et reste à la racine : il pose l'entité `User`, que vous étendez
comme n'importe laquelle des vôtres, si bien qu'il vit avec le code qui l'étend plutôt
qu'avec ce que le CLI se contente de poser.

```
src/
├── articles/          la feature que vous avez engendrée
├── auth/               posé par `rbs add auth`, à la racine par exception
└── modules/
    ├── mod.rs           le point de montage, ouvert au premier fragment installé
    ├── jobs/            posé par `rbs add jobs`
    └── mail/            posé par `rbs add mail`
```

**Un projet créé avant la 1.3.0 garde ses modules exactement là où il les a reçus.** `rbs`
ne les déplace pas — réécrire vos `use crate::mail::…` reviendrait à toucher à un AST
que le CLI s'interdit — mais si un tel projet reçoit ensuite un fragment rangé sous
`src/modules/`, il porte les deux dispositions à la fois. `rbs doctor` le signale par un
nouveau contrôle, `disposition`, qui avertit sans jamais faire échouer la commande :

```
! disposition   hors de src/modules/ : src/mail
    posés par une version antérieure ; rbs ne les déplacera pas — déplacez-les et corrigez leurs `use` si vous voulez une disposition unique
```

Le remède reste manuel : déplacer le répertoire à la main, puis corriger les `use` que lui
seul connaît.

## Trois fragments citent en dur le chemin d'un autre module

La garantie ci-dessus — vos modules restent où ils sont — tient pour un fragment installé
seul. Elle ne tient plus pour trois d'entre eux, qui visent un autre module par son chemin
rangé :

- `webhooks` livre au registre de `jobs` une entrée posée à l'ancre `<rbs:jobs>`, qui vit
  désormais dans `src/modules/jobs/mod.rs`. Sur un projet portant encore `src/jobs/` d'une
  version antérieure, `rbs add webhooks` **échoue** aussitôt — `src/modules/jobs/mod.rs
  est introuvable` — sans bloc à coller : ce message n'a pas de remède automatique, à la
  différence d'une ancre manquante dans un fichier présent. Rien n'est écrit, au moins.
- `scheduler` dépose un `use crate::modules::jobs::{self, Job};` et `rate-limit` un appel
  à `crate::modules::cache::Config::load()?` quand le projet porte aussi `redis`. Ici,
  rien n'empêche l'installation : elle se déclare réussie, puis laisse un `use` ou un
  appel qui ne compile pas. `rbs doctor` le signale après coup, mais l'installation, elle,
  aura dit « réussi ».

Sur un projet créé avant la 1.3.0, déplacez donc `src/jobs/` (et, si vous ajoutez aussi
`rate-limit`, `src/cache/`) sous `src/modules/` et corrigez leurs `use` **avant**
d'installer `webhooks`, `scheduler` ou `rate-limit` — dans cet ordre, l'un des trois
refuse de s'installer et les deux autres installent du code qui ne compile pas.

## `generate crud` ferme ses routes dès que le projet porte `auth`

Sur un projet portant la feature `auth`, `rbs generate crud` n'engendre plus une seule
route publique. Les six routes du CRUD — `list`, `filter`, `create`, `find`, `update`,
`delete` —, neuf lorsque `--with-upload` ajoute la route de contenu, prennent chacune un
paramètre `identite: Identity`, ouvrent leur corps par `identite.require_role(Role::User)?`,
portent `security(("bearer" = []))` et déclarent une 401 et une 403 dans leur
`#[utoipa::path]`. Le contrôleur engendré porte en outre un bandeau de tête de quatre lignes
qui dit ce régime et comment en sortir.

`--role admin` ne décide plus *si* les routes sont gardées, mais jusqu'où : il relève le
seuil de `create`, `update`, `delete` et du `PUT` de la route de contenu au rôle nommé, les
lectures — `list`, `filter`, `find`, `GET` et `HEAD` — gardant le `Role::User` par défaut.

**Ce qui passe au rouge : un rendu attendu.** Si vous comparez la sortie de
`rbs generate crud` à une référence — un test d'or, un `git diff` de CI sur un projet
régénéré, un instantané pris à la main —, elle diverge sur tout projet portant `auth` :
`src/<nom>/controller.rs` et `src/<nom>/tests.rs` changent tous les deux. Un projet **sans**
`auth` rend exactement ce qu'il rendait, octet pour octet ; rien n'est à reprendre de ce
côté.

Ouvrir une route au public est désormais l'édition, et non le défaut : sur le handler à
ouvrir, retirez le paramètre `identite`, l'appel à `require_role`, l'entrée `security` et
les réponses 401 et 403 de son annotation.

`rbs` ne réécrit aucun fichier qu'il a déjà écrit : **un CRUD engendré avant cette version
reste grand ouvert**, y compris sur un projet qui installe `auth` ensuite. `rbs add auth`
nomme désormais, au moment de planifier, les features déjà présentes qui restent publiques,
pour qu'on sache lesquelles fermer à la main.

## `require_role` compare un seuil ; les projets antérieurs comparent une égalité

La garde posée par `add auth` compare désormais un seuil : elle laisse passer dès que le
rôle porté est supérieur ou égal au rôle exigé, si bien qu'un `Admin` satisfait un
`require_role(Role::User)`. Sans cela, le `Role::User` que `generate crud` nomme sur ses
lectures en fermerait la porte aux administrateurs.

L'enum `Role` dérive donc `PartialOrd, Ord`, et **l'ordre de déclaration de ses variantes
porte la hiérarchie** : un rôle inséré entre deux autres déplace d'un coup le seuil de
toutes les gardes du projet. Un rôle plus étendu que le dernier s'ajoute en fin
d'énumération.

**Les deux sémantiques coexistent selon la date du projet.** Un projet neuf reçoit le
seuil ; un projet engendré avant la 1.3.0 garde l'égalité stricte, parce que `rbs` ne
réécrit pas `src/auth/guard.rs` une fois qu'il l'a posé. Pour faire passer un projet
existant, quatre lignes de `src/auth/guard.rs` :

```diff
 pub trait RequireRole {
-    /// Rend [`Error::Forbidden`] si l'appelant ne porte pas `expected`.
-    fn require_role(&self, expected: Role) -> Result<()>;
+    /// Rend [`Error::Forbidden`] si l'appelant porte un rôle inférieur à `minimum`.
+    fn require_role(&self, minimum: Role) -> Result<()>;
 }

 impl RequireRole for Identity {
-    fn require_role(&self, expected: Role) -> Result<()> {
+    fn require_role(&self, minimum: Role) -> Result<()> {
         // Un rôle que l'enum ne connaît plus vient d'un jeton signé par une version
         // antérieure du projet : il n'ouvre rien, et ne fait pas tomber le serveur.
         let porte = Role::try_from_value(&self.role).map_err(|_| Error::Forbidden)?;

-        if porte == expected {
+        if porte >= minimum {
             Ok(())
         } else {
             Err(Error::Forbidden)
         }
     }
 }
```

et, dans `src/auth/model.rs`, la ligne du `derive` de l'enum — sans elle, `>=` ne compile
pas :

```diff
-#[derive(Clone, Debug, PartialEq, Eq, EnumIter, DeriveActiveEnum)]
+#[derive(Clone, Debug, PartialEq, Eq, PartialOrd, Ord, EnumIter, DeriveActiveEnum)]
 #[sea_orm(rs_type = "String", db_type = "String(StringLen::None)")]
 pub enum Role {
```

Avant de dériver `Ord`, relisez l'ordre de vos variantes : c'est lui qui décide, et non le
nom des rôles. Après la bascule, chaque `require_role(Role::X)` déjà écrit dans vos
handlers admet en plus tous les rôles déclarés **après** `X` — c'est précisément le point,
mais il vaut d'être constaté sur vos propres routes avant d'être déployé.
