# rbs 1.3.0

## `rbs add` range ses modules sous `src/modules/`

Dix fragments écrivaient jusqu'ici à la racine de `src/`, mêlés aux features que vous
engendrez vous-même : `audit`, `cache` (le répertoire qu'écrit `redis`), `cors`, `jobs`,
`mail`, `observability`, `rate_limit` (ce qu'écrit `rate-limit`), `scheduler`, `storage`
et `webhooks`. Ils s'installent désormais sous `src/modules/`, dont le point de montage
est `src/modules/mod.rs` — ouvert au premier fragment qui en a besoin, puis retrouvé par
l'ancre `<rbs:modules>` à chaque suivant. C'est la quatorzième ancre, aux côtés des treize
que le CLI connaissait déjà.

`auth` fait exception et reste à la racine : il pose l'entité `User`, que vous étendez
comme n'importe laquelle des vôtres, si bien qu'il vit avec le code qui l'étend plutôt
qu'avec ce que le CLI se contente de poser.

```
src/
├── articles/          la feature que vous avez engendrée
├── auth/               posé par `rbs add auth`, à la racine par exception
└── modules/
    ├── mod.rs           le point de montage, ouvert au premier fragment installé
    ├── jobs/            posé par `rbs add jobs`
    └── mail/            posé par `rbs add mail`
```

**Un projet créé avant la 1.3.0 garde ses modules exactement là où il les a reçus.** `rbs`
ne les déplace pas — réécrire vos `use crate::mail::…` reviendrait à toucher à un AST
que le CLI s'interdit — mais si un tel projet reçoit ensuite un fragment rangé sous
`src/modules/`, il porte les deux dispositions à la fois. `rbs doctor` le signale par un
nouveau contrôle, `disposition`, qui avertit sans jamais faire échouer la commande :

```
! disposition   hors de src/modules/ : src/mail
    posés par une version antérieure ; rbs ne les déplacera pas — déplacez-les et corrigez leurs `use` si vous voulez une disposition unique
```

Le remède reste manuel : déplacer le répertoire à la main, puis corriger les `use` que lui
seul connaît.
