# Contributing to rbs

Thanks for taking the time. This page tells you what you need installed, how to run the
checks CI will run, and the conventions the repository holds itself to.

*[Version française](CONTRIBUTING.fr.md).*

## Contributing without Node

**Working on the Rust code never requires Node.** The documentation site lives entirely
under `docs/`, with its own toolchain and its own workflow; nothing in `cargo build`,
`cargo test`, `cargo clippy` or `cargo fmt` reaches into it, and the Rust CI job runs no
`npm` command. If you only touch the crates or the templates, ignore `docs/` altogether.

The reverse holds too: fixing a typo in the documentation does not require a Rust
toolchain.

## Requirements

| | |
|---|---|
| Rust | 1.85 or later — the MSRV is declared in `Cargo.toml` and enforced by CI |
| Docker | integration tests only; they start a PostgreSQL container |
| Node | documentation site only — see above |

## Everyday commands

```bash
cargo build --workspace
cargo test --workspace                                 # fast tests, no Docker
cargo clippy --workspace --all-targets -- -D warnings   # blocking in CI
cargo fmt --all --check                                 # blocking in CI
```

Run the CLI from the checkout with `cargo run -p rbs-cli -- <command>`, for instance
`cargo run -p rbs-cli -- new demo-api`.

Narrow the test run when you are iterating:

```bash
cargo test -p rbs-core                              # one crate
cargo test -p rbs-core error::tests                 # one test module
cargo test -p rbs-core -- --exact <path::to::test>  # one test
```

## The three levels of testing

1. **`rbs-core`** — plain unit tests, including error-to-HTTP-response conversions.
2. **The generated project** — `rbs generate crud` emits HTTP integration tests covering
   the full CRUD against the application mounted in memory. A starter that generates code
   without tests teaches people not to write any.
3. **The CLI, end to end** — `assert_cmd` drives `rbs new`, then `rbs generate crud`, then
   `rbs add` on a throwaway project, builds it and runs its tests against a real
   PostgreSQL. This is the only test that proves rbs works.

The third level is slow and needs Docker, so it is marked `#[ignore]` and runs on demand:

```bash
cargo test --workspace -- --ignored        # 17 tests, several minutes, Docker required
```

CI runs both, on every pull request. If you cannot run the ignored tests locally, say so
in your pull request — do not silence them.

## Conventions

**Commits follow [Conventional Commits](https://www.conventionalcommits.org), and nothing
else:** `type(scope): subject`. Subjects are written **in French**, imperative, no leading
capital, no trailing period — the repository's history is in French. Types in use: `feat`,
`fix`, `docs`, `test`, `refactor`, `perf`, `ci`, `build`, `chore`.

The body carries the technical *why* of the change and, under a `Vérifications :` heading,
the commands you ran with their real output.

Work on a dedicated branch, never on `main`.

**Code style:**

- A comment explains *why*, never *what*. A comment that paraphrases the next line gets
  deleted.
- `rbs-core` carries `#![warn(missing_docs)]`: public items get a one-to-three-line `///`.
  That is the only exception to the rule above.
- Code generated by the CLI comments its extension points only. No "generated, do not
  edit" banner — that code is meant to be edited.
- A feature file past ~200 lines is a feature that wants splitting.
- Documentation is bilingual: a page changed in English is changed in French in the same
  commit.

**Architecture:** features depend in one direction only —
`controller → service → repository → model`. A service never touches
`DatabaseConnection`; a controller never builds a SeaORM query.

## Pull requests

Say what the change does and why, and list the commands you ran with their results. If a
criterion could not be verified, write that down rather than leaving it implied — an
honest gap is easier to work with than a claim that does not hold.
