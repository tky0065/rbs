# `rbs add ci` — plan d'implémentation

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:test-driven-development.

**Goal:** Qu'un projet généré reçoive son workflow GitHub Actions par une commande, et que
ce workflow passe sur un projet fraîchement créé.

**Architecture:** E7 a laissé un socle où une feature sans code Rust est un répertoire de
templates : `add` ne nomme aucune feature. E8 n'ajoute donc que
`templates/features/ci/.github/workflows/ci.yml.jinja`.

Le critère porte sur ce que le workflow constate, pas sur ce qu'il contient : il lance
`cargo fmt --check` sur le projet généré, qui aujourd'hui **échoue**. Corriger le squelette
fait donc partie de la tâche, faute de quoi le critère est inatteignable.

**Tech Stack:** Rust, `minijinja`, GitHub Actions, `act`, Docker.

**Spec:** `docs/superpowers/specs/2026-08-25-rbs-design.md` §4.1 · conséquence assumée de
D7 (PostgreSQL 18, l. 38).

## Global Constraints

- Branche dédiée `e8-add-ci`.
- **PostgreSQL 18** en service du workflow, pour la même raison qu'en E7.
- Les tests générés par `generate crud` exigent une base **migrée** et lisent leur URL de
  l'environnement, `.env` étant gitignoré : le workflow porte `RBS_DATABASE__URL` et
  applique les migrations avant `cargo test`.
- minijinja emploie `{@ @}` : les `${{ }}` de GitHub Actions traversent intacts.
- `clippy -D warnings` et `fmt --check` bloquants sur rbs comme sur le projet généré.

## File Structure

- Create: `templates/features/ci/.github/workflows/ci.yml.jinja`
- Modify: `templates/project/migration/src/main.rs.jinja` — deux divergences `rustfmt`
- Modify: `templates/project/src/openapi.rs.jinja` — ordre des imports
- Modify: `crates/rbs-cli/src/templates.rs` — tests du fragment et du formatage
- Modify: `crates/rbs-cli/src/main.rs` — `suite("ci")`

### Task 1: Le squelette est conforme à `rustfmt`

Sans cela, le critère d'E8 ne peut pas être rempli : le workflow échoue sur son premier pas.

- [ ] **Step 1: Écrire le test qui échoue**

```rust
    #[test]
    fn chaque_template_rust_du_squelette_est_conforme_a_rustfmt() {
        // Rendre chaque `*.rs.jinja`, l'écrire dans un fichier temporaire, puis
        // `rustfmt --edition 2024 --check`. Le workflow d'`add ci` lance `cargo fmt
        // --check` sur le projet généré : un squelette non conforme le fait échouer
        // au premier pas, sur du code que le développeur n'a pas écrit.
    }
```

Run: `cargo test -p rbs-cli --bins rustfmt` → Expected: FAIL, trois divergences.

- [ ] **Step 2: Corriger les deux templates, puis vérifier**

Run: `cargo test -p rbs-cli --bins rustfmt` → Expected: PASS.

- [ ] **Step 3: Commit** — `fix(templates): rend le squelette conforme à rustfmt`

### Task 2: Le fragment `ci`

**Interfaces:** aucune signature nouvelle. `Source::feature(None, "ci")` doit rendre une
destination unique, `.github/workflows/ci.yml`.

- [ ] **Step 1: Écrire les tests qui échouent**

```rust
    #[test]
    fn la_source_de_ci_restitue_son_workflow() {
        // destinations == [".github/workflows/ci.yml"]
    }

    #[test]
    fn le_workflow_de_ci_amene_une_base_migree_avant_les_tests() {
        // postgres:18 en service ; l'étape des migrations précède `cargo test`
        // -- les tests générés échouent sur un schéma absent
    }

    #[test]
    fn une_feature_inconnue_nomme_desormais_ci_et_docker() {
        // le message d'`add auth` énumère les deux features installables
    }
```

Run: `cargo test -p rbs-cli --bins` → Expected: FAIL.

- [ ] **Step 2: Écrire la template et le message de suite**

Le workflow calque celui de rbs — checkout, `dtolnay/rust-toolchain@stable` avec
`rustfmt`/`clippy`, `Swatinem/rust-cache@v2`, fmt · clippy · test — plus un service
`postgres:18` avec `pg_isready` en healthcheck, `RBS_DATABASE__URL` en `env:` du job, et
`cargo run -p migration -- up` avant les tests.

`suite("ci")` oriente vers ce qu'il reste à faire : pousser.

- [ ] **Step 3: Vérifier**

Run: `cargo test -p rbs-cli --bins` → Expected: PASS.

- [ ] **Step 4: Commit** — `feat(templates): ajoute la feature ci`

### Task 3: Le critère — `act` sur un projet neuf

- [ ] **Step 1: Dérouler un projet et l'équiper**

```bash
rbs new demo-ci --database-url … --yes
# `rbs-core` n'étant pas publié, le noyau est vendorisé depuis `cargo package`,
# qui résout les héritages de workspace exactement comme crates.io les servira.
rbs add ci
```

- [ ] **Step 2: Jouer le workflow**

```bash
act pull_request -W .github/workflows/ci.yml
```

Consigner la sortie réelle, étape par étape. Un échec de `fmt`, de `clippy` ou d'une
migration est un défaut du squelette ou du workflow, à corriger ici — pas à contourner.

- [ ] **Step 3: Vérifications finales**

```bash
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
```

- [ ] **Step 4: Cocher E8 dans `TODO.md`, avec sa preuve sur une ligne**

- [ ] **Step 5: Commit** — `docs: acte la feature ci`
