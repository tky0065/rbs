# E8 — `rbs add ci` (re-vérification)

## Décision

Aucun code à écrire : la template et ses tests sont en place, seul le critère restait à
prouver. La note `PARTIEL` imputait l'échec à la résolution DNS de la machine — le réseau
est rétabli, mais l'obstacle réel est ailleurs : un projet généré dépend de `rbs-core`,
absent de crates.io, et `--core-path` inscrit un chemin absolu d'hôte que le conteneur
d'`act` ne connaît pas.

Plutôt que de rafistoler le projet généré — vendorer le noyau, réécrire son manifeste —
le dépôt est monté dans le conteneur **à son chemin absolu d'hôte**. Le projet testé est
alors exactement celui que `rbs new` a écrit, ce qui est la question posée.

## Étapes

1. `rbs new` + `rbs add ci` + `rbs generate crud` dans un répertoire vierge.
2. `act push -P ubuntu-latest=catthehacker/ubuntu:act-latest --container-options
   "-v <dépôt>:<dépôt>:ro"`, en **arm64 natif**.

Forcer `linux/amd64` casse le run : le toolcache de l'image expose alors un `node` sous un
chemin `x64` qu'`act` ne place pas dans le `PATH` de ses `docker exec`, et toute action
JavaScript échoue avant d'avoir commencé.

Le CRUD n'est pas un ornement. Un projet issu du seul `rbs new` ne porte aucun test :
`cargo test` y passe à vide, et l'étape `migrations` n'a rien à appliquer. Le workflow
« passait » sans que rien de ce qu'il protège n'ait été exercé.

## Preuve

`🏁 Job succeeded`, les quatre étapes vertes, et trois tests du CRUD passés — dont un
cycle de vie complet à travers l'API, qui ne peut réussir que si la migration a créé la
table contre le service PostgreSQL du workflow.
