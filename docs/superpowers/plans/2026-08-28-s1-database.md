# S1 — `rbs new --database postgres|mysql|sqlite`

**Conception.** Tout ce qui varie d'un moteur à l'autre se rassemble dans un type
`Database`, en un seul module de `rbs-cli` : le nom, la feature `sea-orm`, les schémas
d'URL admis, l'URL par défaut, le service compose. C'est ce qui rendra `S3` et `T3`
courts — ils liront cette table au lieu de rejouer une chasse au `postgres` dans les
templates.

Le flag est un `ValueEnum` clap, de défaut `postgres` : le refus d'une valeur inconnue,
qui nomme les trois admises, vient de l'outil et non d'une erreur maison. `new::Error`
gagne en revanche une variante pour la seule faute que clap ne peut pas voir —
`--database mysql` avec une URL en `postgres://`. Elle se lève dans la phase de
vérification, donc **avant le premier rendu** : la garantie « un échec laisse le disque
intact » tient sans code supplémentaire.

Le choix se persiste dans `[package.metadata.rbs] database`. **Son absence se relit en
`postgres`** — c'est le troisième critère, aucun projet existant ne change — et c'est ce
qui donne à `rbs add docker`, `rbs add ci` et plus tard à `doctor` le moyen de savoir sur
quel moteur ils travaillent : `add` ne construit aujourd'hui son contexte de rendu qu'avec
le nom du projet.

SQLite n'a pas de serveur : le compose du fragment `docker` rend le service `app` seul,
et `rbs dev` n'a plus de base à attendre. Docker garde son autre rôle, conteneuriser
l'application.

**Hors périmètre, et à ne pas confondre avec un manque :** le gabarit de migration garde
`Expr::cust("uuidv7()")`, qui est `S2`. À la sortie de S1, un projet SQLite **compile**
mais ne migre pas. Le critère dit « compile ».

## Étapes

1. `crates/rbs-cli/src/database.rs` : l'enum, sa table (nom, feature `sea-orm`, schémas
   admis, URL par défaut, service compose), `FromStr`/`ValueEnum`. Tests unitaires : les
   trois valeurs, la feature de chacune, l'URL par défaut, la détection d'un schéma
   étranger au moteur.
2. `metadata.rs` : champ `database` dans `Metadata`, lu de `[package.metadata.rbs]`.
   Test : un manifeste sans la clé se relit en `postgres`.
3. `cli.rs` et `prompts.rs` : le flag `--database`, et l'URL par défaut proposée en
   interactif qui suit le moteur choisi.
4. `new.rs` : `Options.database`, la variante d'erreur, le contrôle avant rendu, les
   variables `database` et `sea_orm_feature` au contexte. Tests : l'URL étrangère refusée
   **sans rien écrire sur le disque** ; sans le flag, le manifeste rendu porte
   `sqlx-postgres` et `database = "postgres"`.
5. Templates du squelette : les deux `Cargo.toml.jinja`, `.env.jinja`, `.env.example.jinja`,
   et la ligne `database` de `[package.metadata.rbs]`.
6. `add/mod.rs` : `database` au contexte de rendu, lu des métadonnées. Compose et CI du
   fragment branchés. Test unitaire : sur un projet SQLite, le compose rendu n'a pas de
   service `db`.
7. `dev/` : pas d'attente de la base quand le moteur est SQLite.
8. `integration_new` : trois projets, **une cible par moteur** — PostgreSQL garde
   build + test + clippy + rustfmt, MySQL et SQLite s'arrêtent à `cargo build --workspace`.
   Plus un test du refus d'une valeur inconnue sur le binaire livré.
9. Preuves : les trois `cargo build` verts ; le refus nommant les trois valeurs ;
   `rbs new` sans flag → manifeste inchangé sur `sqlx-postgres`.
