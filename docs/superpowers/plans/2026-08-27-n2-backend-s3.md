# Backend S3

## Ce qui s'ajoute au fragment

- `s3.rs.jinja` → `src/storage/s3.rs` : `StockageS3`, quatre méthodes sur `aws-sdk-s3`.
- `mod.rs.jinja` : `StorageConfig` gagne `bucket`, `region`, `endpoint`,
  `access_key_id`, `secret_access_key` et `force_path_style` ; `construire` gagne son
  bras `"s3"`.
- `feature.toml` : `[[dependances]] aws-sdk-s3 = "1.144"`, et les `RBS_STORAGE__*` du
  backend S3 dans `.env.example`.

## Décisions

- **Les identifiants viennent de la configuration**, jamais de la chaîne de fournisseurs
  par défaut d'`aws-config` : celle-ci est asynchrone et interroge le service de
  métadonnées de l'instance. `AppState::new` est synchrone (§2.4 de la conception du
  jalon) et ne peut donc ni la lancer ni l'attendre — c'est ce qui rend la construction
  incapable de joindre le réseau, et non une promesse tenue à la main.
- **Le refus d'un backend inconnu est écrit à la main**, dans `construire`, et n'est pas
  délégué à une énumération `serde` : le message de serde nommerait déjà les variantes
  admises, et un test qui le lirait ne prouverait rien du code du fragment.
- `supprimer` reste idempotent : `DeleteObject` réussit sur une clé absente, comme le
  backend fichiers.

## Preuve de l'absence de réseau

Le test est un `#[test]` **sans boucle Tokio** : le SDK ne pourrait attendre aucune
réponse. L'endpoint pointe sur `http://127.0.0.1:1`, port fermé, et les identifiants sont
faux — toute tentative de connexion rendrait donc une erreur au lieu du `Ok` attendu. Un
budget de temps strict couvre le cas d'une erreur avalée.

## Ordre

1. Les deux tests, puis `rbs new` + `rbs add storage` + `cargo test` → échec.
2. `s3.rs.jinja`, les champs de configuration, le bras `"s3"` → vert.
3. clippy, rustfmt sur le projet généré.
4. Morsures : joindre réellement le réseau dans le constructeur, puis remplacer le refus
