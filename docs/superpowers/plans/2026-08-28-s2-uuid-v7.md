# S2 — Identifiant v7 posé par l'application

**Conception.** `uuidv7()` n'a d'équivalent à écrire ni en MySQL ni en SQLite : le défaut
de colonne quitte la migration pour le code généré.

Le point où l'écrire est un seul par entité. Tous les chemins d'insertion du projet passent
par `..Default::default()` — le service d'un CRUD, son seed, `enfiler` du fragment `jobs`,
la création d'un utilisateur et celle d'un refresh token dans `auth` — et la macro
`DeriveEntityModel` fait déléguer `Default::default()` à `ActiveModelBehavior::new()`.
Surcharger `new()` couvre donc les cinq sans toucher un seul appelant :

```rust
impl ActiveModelBehavior for ActiveModel {
    fn new() -> Self {
        Self { id: Set(Uuid::now_v7()), ..ActiveModelTrait::default() }
    }
}
```

`new()` est synchrone — pas d'`async_trait` dans un fichier que l'utilisateur lit — et la
ligne `impl ActiveModelBehavior for ActiveModel {}` existe déjà comme point d'extension.
Le chemin `update` construit son `ActiveModel` par `From<Model>`, qui rend l'`id` en
`Unchanged` : il n'est pas réécrit.

Le plancher de `doctor` descend à **PostgreSQL 14**. Ce que le code généré exige après S2 —
`uuid`, `timestamptz`, `CURRENT_TIMESTAMP` — est bien plus ancien ; 14 est la plus vieille
version encore supportée par la communauté. Le contrôle garde ainsi une cause vraie, là où
un plancher à 17 ne serait justifié que par le test qui le cite.

## Étapes

1. Test d'intégration d'abord, sous conteneur : deux entités créées à la suite ont des
   identifiants **croissants**. Une assertion de présence d'UUID ne prouverait rien.
2. `feature/migration.rs.jinja`, `features/auth/migration.rs.jinja` (deux tables),
   `features/jobs/migration.rs.jinja` : `.default(Expr::cust("uuidv7()"))` retiré.
   Test unitaire : le rendu ne porte plus `uuidv7`.
3. `feature/model.rs.jinja` et les modèles d'`auth` et de `jobs` : `fn new()` posant
   `Uuid::now_v7()`. Test unitaire : le rendu porte `now_v7()`.
4. `project/Cargo.toml.jinja` : `uuid` passe de `[dev-dependencies]` avec `v4` à
   `[dependencies]` avec `v7`, et le commentaire qui justifiait `v4` se réécrit.
5. `doctor/base.rs` : `MINIMUM` à `140_000`, commentaire et message n'invoquant plus
   `uuidv7()`. Tests de `doctor` mis à jour.
6. Conteneur des tests d'intégration de PostgreSQL 18 à **17**, et les trois commentaires
   d'en-tête qui justifiaient 18 par `uuidv7()`. Aide de la question interactive aussi.
7. Les trois exemples régénérés, `integration_examples` vert.
8. Preuves : les identifiants croissants sous conteneur ; `rbs migrate up` sur
   PostgreSQL 17 ; `integration_examples` vert.
