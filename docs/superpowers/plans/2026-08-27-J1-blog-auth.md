# `examples/blog-auth` — plan d'implémentation

> **Pour un agent :** exécution inline dans la session, `superpowers:executing-plans`.
> Les étapes portent des cases à cocher.

**But :** un second exemple versionné, `examples/blog-auth`, où les mutations d'articles
sont réservées à `require_role(Role::Admin)` — source des extraits de la page de
documentation que `J3` écrira, et compilé par la CI.

**Architecture :** l'exemple est engendré par les commandes du CLI (`new` → `add auth` →
`generate crud`), puis édité à la main sur trois fichiers seulement. Le test de non-dérive
`integration_examples` se généralise à une table de descripteurs : il compare octet à
octet tout ce que le CLI produit, et soumet les trois fichiers édités à des assertions de
contenu plutôt qu'à la comparaison.

**Pile :** Rust, `assert_cmd`, `tempfile`, GitHub Actions.

**Spec :** `docs/superpowers/specs/2026-08-25-rbs-design.md` ; tâche `J1` de `TODO.md`.

## Contraintes globales

- Les projets d'`examples/` ne sont pas membres du workspace racine (`exclude =
  ["examples"]`) : la CI les compile par une étape dédiée.
- `rbs add` refuse un working tree sale — le projet doit être commité entre `new` et `add`.
- `--core-path` est canonicalisé en chemin absolu ; l'exemple versionné le rend relatif.
- Le `.gitignore` du projet généré ignore `.env`, que l'exemple doit pourtant porter :
  `git add -f`, et le `.gitignore` n'est pas touché.
- `Cargo.lock` est versionné (compilation à dépendances figées) et hors comparaison.
- `clippy --all-targets -- -D warnings` et `fmt --check` propres, dans le dépôt comme dans
  l'exemple.

- [ ] **Étape 3 — un test des marques d'édition**

Sans lui, l'exclusion serait une porte ouverte : un `require_role` perdu au fil des
régénérations ne serait signalé par rien.

```rust
#[test]
fn les_editions_a_la_main_de_blog_auth_sont_en_place() {
    let racine = common::depot().join("examples/blog-auth");
    let controller = lire(&racine, "src/articles/controller.rs");

    assert_eq!(
        controller.matches("require_role(Role::Admin)").count(),
        3,
        "les trois mutations doivent porter la garde"
    );
    assert!(!controller.contains("pub async fn list(identite"));

    let guard = lire(&racine, "src/auth/guard.rs");
    assert!(!guard.contains("#[allow(dead_code)]"));

    let tests = lire(&racine, "src/articles/tests.rs");
    assert!(tests.contains("sans_jeton_la_creation_rend_401"));
    assert!(tests.contains("un_user_ne_peut_pas_creer_403"));
}
```

### Tâche 2 : l'exemple lui-même

**Fichiers :**
- Créer : `examples/blog-auth/**` (engendré)
- Éditer à la main : `examples/blog-auth/src/articles/controller.rs`,
  `examples/blog-auth/src/auth/guard.rs`, `examples/blog-auth/src/articles/tests.rs`

- [ ] **Étape 1 — engendrer**

```bash
cargo run -p rbs-cli -- new blog-auth --yes \
  --core-path ./crates/rbs-core \
  --database-url 'postgres://rbs:rbs@localhost:5432/blog_auth'
cd blog-auth && git add -A && git commit -q -m 'projet neuf'
cargo run --manifest-path ../Cargo.toml -p rbs-cli -- add auth
cargo run --manifest-path ../Cargo.toml -p rbs-cli -- generate crud articles \
  --fields 'title:string,body:text,published:bool' --yes --force
```

Puis : `rm -rf .git`, dépendance `rbs-core` remise en `{ path = "../../crates/rbs-core" }`,
`RBS_AUTH__SECRET` posé dans `.env`, `mv` sous `examples/`.

- [ ] **Étape 2 — protéger les mutations**

Dans `src/articles/controller.rs`, `create`, `update` et `delete` prennent `identite:
Identity` en premier extracteur (avant `ValidatedJson`, qui consomme le corps) et
appellent `identite.require_role(Role::Admin)?`. Leur `#[utoipa::path]` gagne
`security(("bearer" = []))` et les réponses 401 et 403. `list` et `find` sont intacts.

- [ ] **Étape 3 — la garde a un appelant**

Retirer `#[allow(dead_code)]` de `src/auth/guard.rs` et le commentaire qui l'explique :
le fragment prescrit lui-même de le faire dès qu'une route l'utilise.

- [ ] **Étape 4 — les tests de l'exemple s'authentifient**

`src/articles/tests.rs` reçoit un harnais qui inscrit un admin, se logue et rend son jeton
d'accès ; les mutations posent l'en-tête `Authorization`. Deux tests s'ajoutent :
`sans_jeton_la_creation_rend_401` et `un_user_ne_peut_pas_creer_403`.

- [ ] **Étape 5 — restaurer les marqueurs de région et vérifier**

Lancer : `cd examples/blog-auth && cargo clippy --workspace --all-targets -- -D warnings`
Attendu : SUCCÈS, zéro warning.

Lancer : `cargo test -p rbs-cli --test integration_examples`
Attendu : SUCCÈS — la comparaison passe pour les deux exemples.

- [ ] **Étape 6 — suivre les fichiers**

`git add -A examples/blog-auth && git add -f examples/blog-auth/.env`, puis relancer
`chaque_fichier_de_l_exemple_est_suivi_par_git`.
