# `rbs doctor` — plan

**But :** diagnostiquer un projet généré — ancres en place, `.env` complet, versions
cohérentes, base joignable et assez récente — et dire quoi faire quand ça cloche.

**Approche :** quatre contrôles indépendants, chacun rendant un `Controle` porteur de son
état, de son détail et, en cas d'échec, de son remède. Le rapport n'interrompt rien : un
diagnostic dit tout ce qui cloche en une passe, pas la première chose venue. Le code de
sortie est non nul dès qu'un contrôle échoue, pour que `rbs doctor` serve en CI.

Les deux premiers contrôles ont déjà leur référence dans le dépôt : `ancres::ANCRES` fait
foi pour les cinq points d'insertion, et le `.env.example` du projet pour les variables
attendues. Aucun des deux n'est réécrit ici.

Le contrôle de la base suit D11 : rbs ne parle pas SQL. La joignabilité se lit d'une
connexion TCP — immédiate, sans compilation — et le numéro de version vient du binaire de
la crate `migration`, qui gagne une commande `version`. Une crate qui ne compile pas est
alors elle-même un diagnostic, pas un échec de `doctor`.

**Hors périmètre :** aucune réparation automatique. `doctor` montre le bloc à recoller ;
c'est l'utilisateur qui le colle. Réécrire un fichier sur la foi d'un diagnostic
contredirait la séquence lire → planifier → vérifier → afficher → appliquer.

## Fichiers

| Chemin | Rôle |
|---|---|
| `crates/rbs-cli/src/doctor/mod.rs` | `Controle`, `Etat`, `Rapport`, orchestration |
| `crates/rbs-cli/src/doctor/ancres.rs` | les cinq ancres, remède = le bloc à recoller |
| `crates/rbs-cli/src/doctor/env.rs` | `.env` confronté à `.env.example` |
| `crates/rbs-cli/src/doctor/versions.rs` | `metadata.rbs.version` contre celle du CLI |
| `crates/rbs-cli/src/doctor/base.rs` | TCP, puis `migration -- version` |
| `crates/rbs-cli/src/doctor/rendu.rs` | rapport aligné, remèdes en dessous |
| `templates/project/migration/src/main.rs.jinja` | commande `version` |

## Étapes

- [x] `doctor/mod.rs` : `Controle`, `Etat`, `Rapport::reussi()`.
- [x] `doctor/ancres.rs` : ancre absente signalée avec son fichier et son bloc — c'est le
      critère ✓ de la tâche. Une ancre dont seule la fermeture manque compte pour absente.
- [x] `doctor/env.rs` : clé de `.env.example` absente du `.env` signalée ; clé
      supplémentaire tolérée, un projet a le droit d'avoir ses variables.
- [x] `doctor/versions.rs` : projet plus récent que le CLI, ou l'inverse, tous deux dits.
- [x] `doctor/base.rs` : URL découpée en hôte et port (5432 par défaut), TCP avec délai
      borné, puis `server_version_num` ; en deçà de 180000, échec nommant la version lue.
- [x] `templates/project/migration/src/main.rs.jinja` : commande `version`.
- [x] `doctor/rendu.rs` et câblage de `main.rs`, code de sortie 1 si un contrôle échoue.

## Preuves attendues

- ✓ *Test : une ancre supprimée est signalée avec le bloc à recoller* — test unitaire sur
  un projet déroulé par `new::creer` dont une ancre a été retirée.
- Bout en bout sur un projet neuf contre PostgreSQL 18 en conteneur.
- Non régression : `cargo test --workspace -- --include-ignored`, `clippy -D warnings`,
  `fmt --check`.
