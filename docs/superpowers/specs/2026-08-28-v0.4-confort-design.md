# v0.4 — Confort : conception du jalon

**Statut** : conception validée le 2026-08-28. Détaille `rbs seed`, `rbs dev`,
`rbs add jobs` et le support de MySQL et SQLite.

Autorité de rang inférieur à `2026-08-25-rbs-design.md`, qu'il précise sans le contredire.

## 1. Pourquoi ce jalon a besoin d'un design

Le `ROADMAP` énonce quatre intitulés et aucun critère de sortie — v0.4 est le premier
jalon dans ce cas. L'exploration du dépôt montre que ces quatre intitulés ne sont pas de
même nature, et que trois d'entre eux tiennent sur le moule éprouvé en v0.3 quand le
quatrième le déborde de très loin.

Le couplage à PostgreSQL se mesure :

```
204 occurrences de (postgres|PostgreSQL|uuidv7) sur 58 fichiers
```

Cinq de ces fichiers sont dans **`rbs-core`** — `db.rs`, `config.rs`, `state.rs`,
`health.rs`, `extract.rs`. Le cas de `db.rs` est le plus net : `ConnectError` est un type
public dont le message d'erreur écrit « vérifiez que le serveur PostgreSQL est démarré ».
Trois autres verrous vivent hors du noyau :

1. **La clé primaire de toute table générée.** `templates/feature/migration.rs.jinja` pose
   `default(Expr::cust("uuidv7()"))`, du SQL brut que seul PostgreSQL 18 comprend. MySQL 8
   n'offre que `UUID()`, qui rend une v1 non ordonnée ; SQLite n'offre rien. **Ce verrou
   n'a pas de solution par dialecte** — il n'existe pas de `uuidv7()` à écrire dans les
   deux autres moteurs.
2. **Les deux manifestes** figent `sea-orm` et `sea-orm-migration` en
   `features = ["sqlx-postgres"]`.
3. **Les quatre tests d'intégration et les trois exemples** lancent un conteneur
   PostgreSQL et portent `uuidv7()` dans leurs migrations committées.

Ce jalon a donc besoin d'un design pour la même raison que v0.3 : pour borner l'endroit
où le noyau s'ouvre, et rendre le critère de sortie exécutable plutôt que relu.

## 2. Décisions

### 2.1 Un seul lot autorisé à modifier `rbs-core`

Le dispositif inventé par v0.3 est repris tel quel, et déplacé : c'est le lot `S`
— la portabilité — **et lui seul** qui peut ouvrir le noyau. Il n'a pas le choix
(§1), et les quatre autres lots n'en ont aucun besoin. Cette autorisation bornée est ce
qui rend le critère de sortie mesurable par un diff (§2.9).

### 2.2 La portabilité ferme le jalon, et ce que cela coûte

Trois lectures étaient ouvertes ; la troisième a été retenue sur arbitrage :

- *Sortir la portabilité vers un jalon v0.5*, avant v1.0 — car geler l'API publique de
  `rbs-core` avec un `ConnectError` qui nomme PostgreSQL graverait le couplage dans le
  contrat de compatibilité.
- *La traiter en premier*, pour que seeds, `rbs dev` et jobs naissent déjà multi-bases.
- **Retenu — la traiter en dernier lot du jalon.** Trois chantiers qui apportent une
  valeur visible livrent avant un chantier d'infrastructure.

Le coût est réel et se nomme : **le lot `R` va poser du SQL que `S` devra porter.** La
table `jobs` naîtra avec `uuidv7()` et `timestamp_with_time_zone`, et son dépilage avec
`SELECT … FOR UPDATE SKIP LOCKED`.

Il s'amortit par une contrainte inscrite dans `R3` : **le dépilage est isolé dès le
premier jour dans une fonction unique**, `reserver_prochain_job`. `S3` n'a alors qu'un
corps de fonction à trois branches à écrire, au lieu d'une chasse à la requête dans le
worker. `P` est à l'abri par construction (§2.4) et `Q` ne touche à aucune base.

### 2.3 Les jobs : une table, et non Redis ni la mémoire

Trois supports étaient ouverts ; la table en base est retenue :

- *Redis*, dont le pool est déjà posé par `L1`. Écarté pour deux raisons : le schéma de
  manifeste de fragment (`feature`, `files`, `anchors`, `migration`, `dependencies`,
  `cargo`, `config`, `env`) **n'a aucun champ pour exiger une autre feature** — il
  faudrait l'inventer ; et un job poussé dans Redis survit au rollback de la transaction
  SQL qui le motivait.
- *Une file en mémoire sur tokio*, qui perd les jobs en attente avec le processus. C'est
  `envoyer_detache` à peine habillé, alors que le design de v0.3 a inscrit que v0.4
  apporterait la vraie réponse.
- **Retenu — une table.** Aucune feature préalable, et surtout la seule option qui donne
  **l'atomicité avec le métier** : le message de bienvenue part si et seulement si
  l'inscription a été committée. C'est ce que `R2` prouve, et c'est la justification
  entière du choix.

Le prix — un dépilage à porter sur trois moteurs — sert le jalon plutôt qu'il ne le grève :
la file est le pire cas de portabilité, donc le meilleur test du lot `S`.

`jobs` est un **fragment**, `rbs add jobs`, comme `redis`, `mail` et `storage`. Un worker
de file est exactement ce qu'un projet finit par vouloir modifier ; il appartient donc au
projet, et il ne s'impose pas à qui n'en veut pas.

### 2.4 Les seeds : du Rust typé dans le projet, jamais du SQL

`src/seeds/` est généré dans le projet et passe par les entités SeaORM déjà produites.
Trois conséquences, dans l'ordre où elles comptent :

- **Typé** : un champ renommé casse à la compilation, et non en silence à l'exécution.
- **Portable sans une ligne de SQL** — ce qui met le lot `P` hors d'atteinte de `S`.
- **Modifiable** : c'est du code fait pour être plié au besoin, donc il appartient au
  projet et non au noyau, conformément à la ligne directrice du générateur.

Les seeds ne sont **pas** des migrations. Le mécanisme de migration les emporterait en
production au premier déploiement, et rien dans son fonctionnement ne l'en empêcherait :
`rbs migrate up` ne sait pas distinguer un schéma d'un jeu d'essai. Le garde-fou est
ailleurs — `rbs seed` refuse de s'exécuter sous `RBS_ENV=production` sans `--force`.

La commande suit le motif de `rbs migrate`, qui enveloppe `cargo run -p migration -- <cmd>`
(`migrate/mod.rs:163`) : **le CLI ne parle jamais à la base lui-même**, il lance un binaire
du projet. `rbs-cli` reste sans dépendance vers `rbs-core` et sans client SQL.

### 2.5 `rbs dev` : le watch est embarqué

`watchexec 8.4` entre en dépendance de `rbs-cli`. La raison est la promesse même d'un
starter : `rbs new` puis `rbs dev` doit tourner, et cette promesse se casse net si la
réponse est « installe d'abord bacon ». Déléguer à un outil tiers aurait aussi remis à
l'utilisateur un comportement que rbs prétend fournir.

Le détail qui a décidé entre `watchexec` et un watch maison sur `notify` + `ignore` n'est
ni le debounce ni le filtrage, tous deux faciles : c'est **la coupure du serveur enfant par
groupe de processus**. Un `cargo run` tué sans son enfant laisse le port occupé au
redémarrage suivant, et le geste n'est pas le même sur les trois plateformes de la CI.
C'est ce que `Q2` prouve, et non que le fichier a été vu.

Le prix est assumé : `cargo install rbs-cli` s'alourdit, une fois, pour tout le monde.

### 2.6 `uuidv7()` disparaît, et PostgreSQL 18 cesse d'être exigé

L'identifiant est généré **côté application** — `uuid 1.26` en feature `v7`, posé par le
service à la création. C'est la seule voie : il n'y a pas de dialecte à écrire pour les
deux autres moteurs (§1).

L'effet de bord est un gain, pas une concession. `uuidv7()` imposait **PostgreSQL 18**, ce
que `V1` puis `O4` ont relevé comme une friction de démarrage — « un 17 fait échouer
`rbs migrate up` avant tout test ». Cette exigence tombe avec la fonction.

`S2` le prouve par ce que v7 garantit et que v4 ne garantit pas : deux entités créées à la
suite ont des identifiants **croissants**. Un test qui vérifierait seulement qu'un UUID est
posé passerait avec `new_v4` et ne prouverait rien.

Conséquence sur le squelette : `uuid` et `serde_json` sont aujourd'hui des
**dev-dependencies** (`templates/project/Cargo.toml.jinja`) ; les deux montent en
dépendances de production — `uuid` pour l'identifiant, `serde_json` pour le payload des
jobs. Le commentaire qui explique pourquoi `uuid` était en dev se réécrit, il ne se
supprime pas.

### 2.7 `envoyer_detache` : ni réécrite, ni supprimée

Le design de v0.3 laissait le choix entre deux sorts, et les deux sont mauvais :

- *La réécrire au-dessus de la file* crée un couplage `mail` → `jobs` que le manifeste ne
  sait pas exprimer (§2.3), et casserait `mail` installée seule.
- *La supprimer* retire une fonction à qui n'installe pas `jobs`.

**Troisième voie retenue : la garder, et cesser de mentir sur ce qu'elle fait.** Sa
documentation dit qu'elle perd son message si le processus tombe, et `T2` montre le passage
à un job pour qui veut la garantie. La condition non négociable est que le fragment `mail`
reste utilisable seul.

### 2.8 Le support des trois bases : preuve graduée, pas égalité proclamée

`rbs new --database postgres|mysql|sqlite` produit les trois, et les trois compilent en CI.
Le bout-en-bout est joué par la CI sur PostgreSQL — l'existant — et sur **SQLite**, qui ne
coûte rien : pas de conteneur, un fichier. MySQL reçoit un test `#[ignore]` sous conteneur,
lancé à la main, exactement comme `L3`, `M3` et `N3` le sont déjà.

La mesure de `J2` interdit l'égalité stricte : la cible de compilation partagée fait que le
total vaut la somme des durées et non leur maximum — 18,71 s étaient passées à 56,79 s pour
un seul test ajouté. Trois back-ends joués par la CI de chaque PR multiplieraient d'autant.

Le gain propre de SQLite est indépendant de la portabilité et le justifierait seul :
`cargo test` d'un projet généré tournerait **sans Docker**, ce qui répond directement aux
frictions de démarrage consignées par `V1`.

### 2.9 Preuve du critère de sortie : deux commandes et deux diffs

Le `ROADMAP` n'énonce pas de critère pour v0.4. Celui-ci est proposé :

1. `rbs new --database postgres|mysql|sqlite`, trois fois, puis `cargo test` sur chacun.
2. Un job enfilé, le processus tué, relancé — **le job s'exécute quand même**. C'est la
   seule chose qui distingue ce jalon du `tokio::spawn` détaché de `M2`, et elle se prouve.

Le bornage du noyau (§2.1) se mesure comme en `O4`, par deux diffs plutôt qu'un seul, `S`
étant au milieu du jalon et non à sa fin :

```
git diff --stat <début du jalon>..<P, Q et R tous trois intégrés> -- crates/rbs-core/  →  0
git diff --stat <fin de S>..HEAD                                  -- crates/rbs-core/  →  0
```

## 3. Dépendances

Versions résolues le 2026-08-28 par `cargo add --dry-run`, et non par `cargo info`, qui
remonte les pré-publications.

| Crate | Version | Portée | Motif |
|---|---|---|---|
| `watchexec` | 8.4.0 | `rbs-cli` | watch de `rbs dev` : debounce, filtrage par gitignore, et coupure du serveur enfant par groupe de processus (§2.5) |
| `uuid` | 1.26.0 | projet, **production** | feature `v7` ; monte de `[dev-dependencies]`, où `v4` reste pour les tests |
| `serde_json` | 1.0.151 | projet, feature `jobs` | payload des jobs ; monte de `[dev-dependencies]` |
| `sea-orm` | 2.0 | projet | features `sqlx-mysql` et `sqlx-sqlite` selon `--database`, en plus de `sqlx-postgres` |

**Aucune dépendance de développement nouvelle**, et aucune entrée dans `rbs-core` : le
seul ajout au CLI est `watchexec`, tout le reste est écrit dans le `Cargo.toml` du projet.

## 4. Découpage et ordre

```
(P ∥ Q ∥ R) → S → T
```

| Lot | Contenu | Ouvre le noyau |
|---|---|---|
| **P** — Seeds | `P1` commande `rbs seed` · `P2` `src/seeds/` au squelette · `P3` seed posé par `generate crud` | non |
| **Q** — `rbs dev` | `Q1` orchestration du démarrage · `Q2` le watch | non |
| **R** — Jobs | `R1` manifeste et table · `R2` enfilage et atomicité · `R3` worker et réessai · `R4` `integration_jobs` | non |
| **S** — Portabilité | `S1` `--database` · `S2` uuid v7 applicatif · `S3` dépilage à trois branches · `S4` le noyau cesse de nommer PostgreSQL | **oui, seul** |
| **T** — Documentation et sortie | `T1` exemple `newsletter-queue` · `T2` pages FR/EN · `T3` `doctor` · `T4` critère de sortie | non |

`P`, `Q` et `R` sont indépendants : trois chantiers sans fichier de fond commun. Deux
réserves, dites plutôt que découvertes : ils se rejoignent sur l'enum `Commands` de
`cli.rs`, à deux lignes chacun ; et **le goulot est entier à la vérification** — cible de
compilation partagée, verrou de cargo, un conteneur par test, comme en v0.3. Trois branches
valent donc le coup pour écrire, à condition de passer les `--ignored` en fin de parcours,
une par une.

`S` suit les trois : il porte ce qu'ils ont posé. `T` suit `S` : la documentation ne peut
pas décrire trois bases avant qu'elles existent.

## 5. Ce que ce design ne tranche pas

- **Le nombre de tentatives avant échec définitif d'un job**, et la forme de l'attente
  entre deux. `R3` propose, l'usage corrigera — c'est une valeur de configuration dans la
  section `[jobs]`, donc modifiable sans toucher au fragment.
- **Le sort de `rbs dev` sous Windows.** Le geste de coupure d'un groupe de processus n'y
  est pas celui d'Unix ; `Q2` doit le prouver sur les trois plateformes, et si le coût
  s'avère disproportionné, la commande peut y dégrader vers un redémarrage sans watch —
  ce qui se dirait dans la documentation, jamais en silence.
- **Si `newsletter-queue` doit porter `mail`.** L'exemple démontre les seeds et les jobs ;
  y ajouter l'envoi réel le rendrait plus parlant mais dépendant d'un conteneur de plus en
  CI. `T1` tranchera sur pièce.
- **Le critère de sortie de v0.4 dans le `ROADMAP`.** Il est proposé en §2.9 ; l'inscrire
  dans le `ROADMAP`, dont le tableau d'état est par ailleurs périmé, est un geste distinct
  de ce design.
