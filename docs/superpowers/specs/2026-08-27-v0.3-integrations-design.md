# v0.3 — Intégrations : conception du jalon

**Statut** : conception validée le 2026-08-27. Détaille `rbs add redis`, `rbs add mail`
et `rbs add storage`, et le lot qui les rend possibles.

Autorité de rang inférieur à `2026-08-25-rbs-design.md`, qu'il précise sans le contredire.

## 1. Pourquoi ce jalon a besoin d'un design

Le `ROADMAP` énonce un critère de sortie qui est aussi un test du travail précédent :

> Trois features suivant le même moule, ajoutées sans toucher au noyau. Si l'une d'elles
> oblige à modifier `rbs-core`, c'est le moule qui est à revoir.

L'exploration du dépôt montre que, prises à la lettre, **les trois features obligeraient
à modifier le noyau**. Trois verrous, trois raisons distinctes :

1. **La configuration.** `Config` (`crates/rbs-core/src/config.rs:27`) énumère ses champs.
   `auth` s'y est ajoutée par `#[cfg(feature = "auth")] pub auth: AuthConfig`, c'est-à-dire
   en modifiant le noyau — c'était la tâche `G3`. Une section `[cache]` posée dans
   `config/default.toml` par le manifeste d'un fragment n'échoue pas au chargement,
   `Config` n'ayant pas `deny_unknown_fields` ; mais rien, dans le projet, ne sait la lire.
2. **Les dépendances tierces.** Le manifeste de fragment sait écrire
   `[cargo.rbs-core] features = ["auth"]`, ce qui **active** une feature sur une dépendance
   déjà déclarée (`manifeste.rs:62`). Ni `redis`, ni `lettre`, ni `aws-sdk-s3` ne figurent
   dans un `Cargo.toml` généré. L'action `PatchToml::AjouterDependance` existe pourtant
   depuis le lot `E` (`plan/action.rs:56`) — elle n'est simplement exposée à aucun manifeste.
3. **L'état partagé.** Les cinq ancres du squelette sont `features`, `routes`, `openapi`,
   `migrations` et `migration_modules`. Aucune n'atteint `state.rs`. Or les trois features
   ont un client à partager entre handlers.

Le troisième verrou porte une bonne nouvelle : `AppState` est **généré**
(`templates/project/src/state.rs.jinja`), le noyau ne possédant que `CoreState` et le trait
`HasCoreState`. Le partage d'un pool ne demande donc rien au noyau — seulement une ancre.

La lecture retenue est celle que le `ROADMAP` prescrit : **c'est le moule qui est à revoir**,
et il se révise une fois, avant les features, dans un lot qui n'en livre aucune.

## 2. Décisions

### 2.1 Un lot de réparation, puis trois features

Le jalon s'ouvre par le lot `K`, qui ne livre aucune feature — exactement comme `H`
précédait `I` au jalon précédent. `K` est **le seul lot autorisé à modifier `rbs-core`**.
Cette autorisation, bornée à un lot, est ce qui rend le critère de sortie mesurable (§2.10).

### 2.2 Configuration : un point d'extension générique, pas un champ par feature

Trois voies étaient ouvertes ; la troisième est retenue :

- *Un champ par feature dans `Config`*, comme `auth`. Cohérent avec l'existant, mais viole
  frontalement le critère de sortie et condamne toute feature tierce à patcher le noyau.
- *Un chargement généré par fragment* : chaque feature dépose son `config.rs` qui relit
  `config/*.toml` et l'environnement pour son compte. Le critère est tenu à la lettre, au
  prix d'une cascade de chargement redupliquée dans chaque fragment, avec la dérive de
  comportement que trois copies finissent par produire.
- **Retenu — le noyau ouvre sa cascade.** `config::figment()` est privée
  (`config.rs:162`) ; elle le reste, mais `rbs-core` expose

  ```rust
  pub fn section<T: DeserializeOwned>(nom: &str) -> Result<T, ConfigError>
  ```

  qui rejoue la même cascade — défauts, `config/default.toml`, `config/{env}.toml`,
  variables `RBS_*` — et en extrait une seule section. Une lecture de fichiers de plus
  au démarrage, et une seule fois : le coût est nul au regard d'une cascade dupliquée.

Conséquence recherchée : **les valeurs par défaut migrent dans la struct générée**
(`#[serde(default = "…")]` sur `CacheConfig`), là où l'utilisateur les lit et peut les
changer, au lieu des `Serialized::default(…)` du noyau où elles sont hors de sa portée.

Cette fonction n'appartient à aucune feature : elle est compilée sans flag, et aucune des
trois features de ce jalon n'apparaît par son nom dans `rbs-core`.

### 2.3 Dépendances tierces : le manifeste apprend à en ajouter

Nouvelle section du `feature.toml`, sur le modèle des existantes :

```toml
[[dependances]]
nom              = "lettre"
version          = "0.11"
default_features = false
features         = ["smtp-transport", "builder", "pool", "tokio1-rustls"]
```

`default_features` fait partie du schéma dès la première version, et non par symétrie avec
`cargo add` : `lettre` active `native-tls` par défaut, donc réclamerait OpenSSL sur les
trois plateformes de la CI. Un schéma sans ce champ rendrait la feature `mail` impossible
à déclarer correctement.

Branchée sur `PatchToml::AjouterDependance`, écrite au lot `E` et restée sans appelant —
la même situation que `AjouterFeatureADependance` avant `H5`, qui lui a donné le sien.
Les garanties de `H5` sont reprises telles quelles : le reste du manifeste n'est pas
reformaté, et les commentaires du développeur survivent au patch.

Les versions sont **figées dans le fragment**, pas déduites : un projet généré doit
compiler dans six mois avec les versions que le fragment a validées.

### 2.4 L'état partagé : deux ancres, et `new` faillible

Deux ancres et non une, parce qu'un champ se déclare et s'initialise à deux endroits :

- `// <rbs:state_champs>` dans la struct `AppState` ;
- `// <rbs:state_init>` dans le corps de `AppState::new`.

Les trois features construisent leur client de façon **faillible mais synchrone** :
`deadpool-redis` bâtit un pool paresseux sans E/S, `AsyncSmtpTransport::relay` rend un
`Result`, le client S3 se dérive d'une configuration déjà résolue. `AppState::new` devient
donc `-> Result<Self, …>`, et **ne devient pas `async`** : rien ne le réclame, et l'ajouter
par précaution contaminerait la signature de tout projet généré.

Un projet créé avant ce lot n'est pas cassé en silence : l'ancre absente déclenche le
comportement établi en `H3` — rien n'est écrit, le bloc à coller s'affiche, sortie en
erreur. Le squelette et les deux exemples sont régénérés par `K3` ; `integration_examples`
compare les exemples à une génération fraîche et tombera tant que ce n'est pas fait.

### 2.5 Périmètre : resserré sur ce que le jalon peut tenir seul

Les intitulés du backlog promettaient plus que le jalon ne peut porter :

| Intitulé d'origine | Retenu | Motif |
|---|---|---|
| redis — « pool, cache, **sessions** » | pool et cache typé | `auth` tient déjà ses sessions en base (`refresh_tokens`, rotation) ; un second mécanisme de session les contredirait. |
| mail — « SMTP, templates, **envoi asynchrone** » | SMTP, gabarits, envoi **détaché** | « asynchrone » suppose une file avec réessai — les jobs en arrière-plan sont en v0.4. Un `tokio::spawn` détaché, sans file ni réessai, est ce que le jalon peut tenir sans mentir. |
| storage — « système de fichiers et S3 » | inchangé | — |

L'objet du jalon est de prouver le moule, non la richesse fonctionnelle. Chaque ligne
retirée ici est une ligne que v0.4 posera sur une base éprouvée.

### 2.6 Le module porte l'usage, pas la techno

`rbs add redis` dépose `src/cache/`, non `src/redis/`. Le squelette insère `mod redis;`
en tête de `main.rs`, et `use redis::Client` y deviendrait ambigu entre le module local et
la crate du même nom (E0659). La raison est d'abord celle-là ; elle en recouvre une
meilleure : le module dit ce qu'il fait, et remplacer Redis par autre chose ne demande
pas de renommer un répertoire.

`mail` et `storage` gardent leur nom, aucune crate du projet ne le portant.

### 2.7 Aucune route, aucune migration

Les trois fragments ne complètent ni `routes`, ni `openapi`, ni `migrations`.

`add storage` qui poserait `POST /files` imposerait une table, un propriétaire et une
politique d'accès : c'est une feature applicative, pas une intégration, et elle décrèterait
à la place de l'utilisateur comment ses fichiers sont possédés. Le fragment livre la brique ;
la route appartient au projet.

Ces trois ancres restent donc inexercées par le jalon. Elles le sont déjà par `auth` — ce
que v0.3 exerce de neuf, ce sont les trois pièces du lot `K`, plus `[[env]]`.

### 2.8 `storage` : un trait de quinze lignes plutôt qu'`object_store`

`object_store 0.14.1` fournirait l'abstraction toute faite, avec Azure et GCS en prime, et
compile plus vite que le SDK AWS. Le trait maison est retenu quand même : il tient en une
quinzaine de lignes **dans le projet de l'utilisateur**, qui peut le lire, le restreindre
ou le remplacer. C'est la ligne directrice du générateur — le noyau porte ce qui ne varie
pas, le projet porte ce qu'on veut modifier — et une abstraction de stockage est
précisément ce qu'un projet finit par vouloir modifier.

Le prix est réel et assumé : `aws-sdk-s3` allonge la compilation de tout projet faisant
`add storage`. Il est payé par ceux qui installent la feature, jamais par les autres.

### 2.9 Preuve : un conteneur réel par feature

Une image par feature sous `testcontainers`, un test `#[ignore]` par feature, sur le modèle
d'`integration_auth` :

- **Redis** pour `L3` — l'expiration se prouve par une attente réelle, non par un double ;
- **Mailpit** pour `M3` — son API HTTP permet de relire le message reçu, donc d'assurer que
  le destinataire, le sujet et le **corps rendu par le gabarit** sont ceux attendus ; un
  transport en mémoire prouverait seulement que le code n'a pas paniqué ;
- **MinIO** pour `N3` — et le même jeu de tests joué contre les deux implémentations du
  trait, ce qui prouve qu'il abstrait réellement au lieu de seulement compiler.

Un test par feature et non un test unique : la feature installée seule est le cas réel de
l'utilisateur, et un échec sur l'une ne doit pas masquer les deux autres.

`J2` a mesuré ce que coûte le partage de la cible de compilation entre tests bout en bout —
18,71 s à 56,79 s après pose du verrou, le total valant la somme des durées et non leur
maximum. Les trois tests s'ajoutent à ce compte, sur Linux uniquement, comme les existants.

### 2.10 Preuve du critère de sortie : un diff

`K` étant le seul lot autorisé à toucher le noyau, le critère du `ROADMAP` devient une
commande :

```
git diff --stat <sha de fin de K>..HEAD -- crates/rbs-core/    →    0 ligne
```

Un lot `L`, `M` ou `N` qui aurait dû patcher `rbs-core` apparaît dans ce diff. Le critère
cesse d'être une intention relue à la main pour devenir une vérification exécutable.

## 3. Dépendances

Versions résolues le 2026-08-27 par `cargo add --dry-run`, et non par `cargo info`, qui
remonte les pré-publications.

| Crate | Version | Portée | Motif |
|---|---|---|---|
| `redis` | 1.6.0 | projet, feature `cache` | client, en `tokio-comp` |
| `deadpool-redis` | 0.23.1 | projet, feature `cache` | pool paresseux, construction infaillible |
| `lettre` | 0.11.23 | projet, feature `mail` | SMTP async, `default-features = false` puis `smtp-transport`, `builder`, `pool`, `tokio1-rustls` — les défauts de la crate activent `native-tls`, qui réclamerait OpenSSL sur les trois plateformes de la CI |
| `minijinja` | 2.24.0 | projet, feature `mail` | gabarits de messages ; déjà la crate de gabarits du CLI |
| `aws-sdk-s3` | 1.144.0 | projet, feature `storage` | implémentation S3 du trait |

Aucune n'entre dans `rbs-core` : toutes sont écrites dans le `Cargo.toml` du projet par le
manifeste du fragment (§2.3).

**Aucune dépendance de développement nouvelle.** Le dépôt lance déjà ses conteneurs par
`testcontainers 0.28.0` en `GenericImage` (`tests/integration_crud.rs:30`), et non par
`testcontainers-modules` : Redis, Mailpit et MinIO se déclarent de la même façon, par leur
image et leur condition d'attente.

## 4. Découpage et ordre

```
K1 ∥ K2 → K3 → (L ∥ M ∥ N) → O
```

| Lot | Contenu |
|---|---|
| **K** — Le moule, deuxième tour | `K1` `config::section::<T>` · `K2` `[[dependances]]` · `K3` ancres d'état |
| **L** — `rbs add redis` | `L1` manifeste et pool · `L2` cache typé · `L3` `integration_redis` |
| **M** — `rbs add mail` | `M1` manifeste et transport · `M2` gabarits · `M3` `integration_mail` |
| **N** — `rbs add storage` | `N1` trait et backend FS · `N2` backend S3 · `N3` `integration_storage` |
| **O** — Documentation et sortie | `O1` exemple · `O2` pages FR/EN · `O3` `doctor` · `O4` critère de sortie |

`K1` ne touche que `rbs-core`, `K2` que `rbs-cli` : aucun fichier partagé, les deux se
mènent en parallèle — le même argument qui a fait mener `G` et `H` ensemble. `K3` suit `K2`,
les deux touchant l'interprète du manifeste.

`L`, `M` et `N` sont disjointes à l'écriture : un répertoire `templates/features/<nom>/` et
un `tests/integration_<nom>.rs` chacune. Leur seul fichier commun est `FEATURES_CONNUES`
(`new.rs:23`), une ligne par feature ; `doctor` n'est touché qu'en `O3`. **Le goulot est
entier à la preuve** : cible de compilation commune, verrou de cargo, un conteneur par test.
Trois branches valent donc le coup pour écrire les fragments, à condition de passer les
`--ignored` en fin de parcours, une par une.

## 5. Ce que ce design ne tranche pas

- **Le nom de la section de configuration de `redis`.** Le module s'appelle `cache` (§2.6) ;
  la section est écrite `[cache]` par cohérence, mais la commande reste `rbs add redis`.
  Si l'écart entre les deux gêne à l'usage, il se corrige en `O2`, quand la documentation
  devra l'expliquer.
- **Le sort d'`envoyer_detache` en v0.4.** Quand les jobs arriveront, cette fonction sera
  soit réécrite au-dessus de la file, soit supprimée. Le fragment ne promet rien à son sujet.
- **Le nombre d'exemples.** `O1` en prévoit un portant les trois features ; s'il s'avère
  illisible, il se scinde — l'installation isolée est de toute façon prouvée par `L3`, `M3`
  et `N3`.
