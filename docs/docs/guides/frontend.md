# Frontend

Two fragments put a Vue 3 application into an existing project. `rbs add frontend` installs
the **base**: the application, its router, a Tailwind v4 theme, fourteen vendored
shadcn-vue components, and a public home page. `rbs add frontend-admin` adds the
**admin shell**: an authenticated space of four account-and-health screens — and, from then
on, [`rbs generate crud`](../cli/generate.md) writes the table's admin screens along with
its entity.

One application, two route regimes: a public root, and the admin space in a lazy chunk
behind a route guard. One build, one static service, one fallback.

Every snippet on this page is taken from
[`examples/admin-console`](https://github.com/tky0065/rbs/tree/main/examples/admin-console),
a project generated by the CLI, compiled in CI, and whose frontend CI installs, type-checks
and builds. Nothing here is written by hand for the documentation.

Two of those lines matter beyond the count. `.gitignore` gains `frontend/node_modules/`
and `frontend/dist/`, so the first `npm install` does not offer you thirty thousand files
to commit. And `Cargo.toml` gains nothing that needs Node: **`cargo build` succeeds on a
machine without it**, which is the counterpart of a purely declarative fragment mechanism —
the CLI never runs a command, so it never runs `npm` either.

## The static service is a module

The base does not throw a fallback into the router's anchor. It installs a module — the
same shape the `cors` fragment uses — that carries its configuration, its routes and
its tests, and the anchor receives one call.

```rust file=examples/admin-console/src/modules/frontend/mod.rs region=repli
```

A fallback rather than named routes is the whole trick: everything mounted elsewhere — your
API, `/health`, the OpenAPI document — is matched before it, so it cannot mask a single
route of the service. It is also what makes a reload on a deep client route render the
application instead of a 404.

```rust file=examples/admin-console/src/modules/frontend/mod.rs region=servir
```

The index file is stat'ed on every request rather than once at startup. That is deliberate:
the bootstrap page erases itself the moment the build lands, with no switch to flip and no
server to restart. The cost is one system call, on the fallback path only.

## The bootstrap page

The fragment mechanism is declarative: no hooks, no command execution. The CLI therefore
cannot install the client's dependencies for you, and the build is absent on the first
`cargo run`. Rather than a 404, the module then serves a self-contained page — no
dependency, system fonts, written in the project's visual world — that prints the project's
name, the real state of its database, and the commands left to type.

It is the constraint turned into a first contact. It disappears on its own.

## Configuration

```toml file=examples/admin-console/config/default.toml region=frontend
```

`dir` is where the build lands, `index` the file the fallback serves for a deep route. Both
follow the project's configuration mechanism, so `RBS_FRONTEND__DIR` overrides `dir`
without touching the file — see [Configuration](./configuration.md).

## The home page

The base's home page is public, and its default content is **true on the first boot**. It
names the real project, queries its health probe for real, links to the OpenAPI
documentation the service already serves, and shows a `curl` command that works. No filler
text, no invented claim: nothing on the page has to be emptied before you can use it.

Its structure is a showcase — probe, try-it, routes, documentation, components — so you can
replace it section by section on the way to a real product page. It stays readable on a
phone, and honours `prefers-reduced-motion`.

## The visual world

The world is **listing paper**: continuous stationery, a perforated margin, impact-ribbon
ink. It is a deliberate refusal of the category standard — charcoal background, mesh
gradient, neon accent — and [ADR-0002](https://github.com/tky0065/rbs/blob/main/docs/adr/0002-monde-visuel-bandes-de-listing.md)
records the three directions turned down along with it.

Three disciplines constrain any later change: a **bande** is a material and not a
background, so no content sits on undifferentiated white; hierarchy is made by scale
contrast alone, with no intermediate level; and every graphic element is a character, a
rule or a perforation.

**No emoji.** Vector icons are admitted where they are an affordance — a menu's chevron, a
dialog's cross, a sort arrow — never as ornament. On the bootstrap page, which has no access
to the npm registry, they are hand-written SVG.

The world is fully tokenised. Replacing it means rewriting one theme block, `@theme` in
`frontend/src/assets/main.css`: no component names a colour, they only know the roles that
block defines.

The order of those last steps is not decoration. **The shell imports the typed client, and
the client is not shipped** — it is generated from *your* project's OpenAPI document by
[`rbs generate client`](../cli/client.md), because one project's
contract is not another's and a frozen client would lie from the first route added. Skip
that command and `npm run typecheck` stops on an import nothing has written.

Nothing else in the shell speaks HTTP:

```ts file=examples/admin-console/frontend/src/api/index.ts
```

### Four screens, each backed by a real route

Sign-in with its password-reset request, a dashboard showing the real probes, the version
and the number of mounted routes read from the OpenAPI document, the open sessions with
single and global revocation, and the profile with its password change. Each is backed by a
route `auth` actually exposes — none of them shows a number nobody serves.

### Token transport, and what it costs

`auth` returns a pair in JSON — a short-lived signed access token, a long-lived opaque
refresh token — presented in the `Authorization` header, with no cookie and no server-side
session. The client therefore keeps **the access token in memory and the refresh token in
local storage**:

```ts file=examples/admin-console/frontend/src/api/jetons.ts region=jetons
```

The price is real and it is accepted: a script injected into this application reads local
storage and walks away with a long-lived session, where the access token would not have
survived the tab. The safe alternative is an `HttpOnly` cookie flow, which means changing
the `auth` fragment on the server side — a separate piece of work, not a setting here. In
the meantime `POST /auth/logout` revokes the session server-side, and the sessions screen
cuts an access you do not recognise.

### State on the client

**Two Pinia stores, and no more**: authentication (tokens, current user, renewal) and
interface (theme, rail state, notifications). Any business resource goes through a
composable on top of the typed client. One store per entity is the reflex Pinia was built
to shed, and it would double the code to copy for every new screen.

## The generated screens

On a project carrying the shell, `rbs generate crud` writes the table's admin screen —
filtered list, form, detail — in addition to the entity, its migration and its closed
routes. **No flag asks for it**: the command reads the installed fragments and adapts its
output, exactly the way it writes closed routes as soon as `auth` is there. `--no-admin` is
the way out, for a table nobody should administer from the interface.

This is a dated reversal of scope. "Generated admin interface" sat in the roadmap's
out-of-scope list from the start; [ADR-0003](https://github.com/tky0065/rbs/blob/main/docs/adr/0003-ecrans-d-administration-engendres.md)
reverses it and repeals [ADR-0001](https://github.com/tky0065/rbs/blob/main/docs/adr/0001-squelette-admin-plutot-qu-interface-engendree.md),
whose cost analysis stays true — only the trade-off changed. What remains out of scope is
the generic engine driven by the OpenAPI document at runtime: screens you cannot personalise
without forking the engine contradict the rule that generated code is made to be modified.
A generated screen belongs to its author the moment it is written.

The screen mounts itself through **two anchors, and two only**. The routing table:

```ts file=examples/admin-console/frontend/src/admin/montage.ts region=montage
```

And the rail, whose entries the shell walks twice — a permanent rail beyond the width of a
laptop, a side panel below it:

```ts file=examples/admin-console/frontend/src/admin/rail.ts
```

There is no third anchor to declare the module: in TypeScript, the import that gives the
route its component *is* the declaration, where Rust wants a `pub mod` separate from the
mount. Both entries above are of the same shape — the first is the demonstration screen the
fragment lays down, the second the one the command generated.

### One template, two producers

The demonstration screen and every generated screen come out of the **same template**. The
fragment renders it once for a demonstration entity; the command renders it for each real
table. What you see at installation time is therefore exactly what you will get next — which
was true of neither of the two alternatives: a shell with no demonstration screen opens on an
empty, silent space, and a demonstration screen distinct from the template diverges from it.

What separates the two producers is a source: four functions, plus the row mapper and the
error phrase. The fragment renders them over a table written into the file; the command
renders them over the typed client:

```ts file=examples/admin-console/frontend/src/admin/vues/Incidents.vue region=source
```

Everything after that — filter, sort, pagination, form, detail, rendering — knows only
`Ligne`, `Requete` and `Formulaire`, and does not change from one table to the next.

### What the form holds

One control per declared column: a text field for a string, a long text, a UUID or a
reference; the browser's number field for an integer or a float; a text field for a decimal,
which the contract carries as a string so a JavaScript number cannot lose the cents; a
checkbox for a boolean; the native date and datetime controls, whose output is exactly the
format the contract wants — the instant's time zone is restored on submit; and a list for an
enumeration, typed as the union of the values it declares.

An optional column may be left empty and then sends `null`, which is the only reading that
lets you clear it from the form.

The filter searches the table's **first textual column**, and a table without one shows no
filter field at all rather than one that filters nothing: the project's filter conjoins its
conditions with AND, and searching a pattern across several columns would want an OR the
contract does not expose.

### Regenerating

The screen is ordinary code you own. Regenerating a table whose columns changed goes through
the usual door: the plan reports the screen as a conflict, and only `--force` overwrites it —
the same contract [`rbs generate client`](../cli/client.md) offers. The
two anchors are idempotent, so a regeneration adds no second route and no second rail entry.

One name is refused: a table called `demonstration`, on a project carrying the shell, would
render its screen onto the demonstration screen's own file and route. The command says so and
names `--no-admin`.

## Development and production

In production the binary serves the build itself: no second server, no reverse proxy. In
development, `npm run dev` serves the client on Vite's port with hot reload, and proxies to
the binary what it does not serve itself:

```ts file=examples/admin-console/frontend/vite.config.ts region=relais
```

A route your project adds — a generated CRUD, for instance — is declared there too, failing
which it will only answer once the build is in place. The proxy is also why the default
setup needs no CORS: the browser sees a single origin. [`rbs add cors`](../cli/add.md#the-sixteen-features) is for the
case where the client is served from *another* origin, which `admin-console` carries so the
configuration is on show.

## Testing

The module ships its own tests into your project, the way `cors` does: the static service's
routing, the fallback onto the application, the non-interception of the API and of the
OpenAPI document, the bootstrap page served when the build is absent and erased when it is
present.

```bash
cargo test --workspace modules::frontend
```

Node is not involved: these are Rust tests over the fallback, and they pass on a machine
that has never seen `npm`.

On rbs's own side, `examples/admin-console` is the only example built twice — in Rust like
the four others, and on the client by a dedicated CI job that regenerates the typed client,
installs the dependencies, type-checks and builds. Without it, several hundred lines of
TypeScript would be compiled nowhere.

## What it leaves to you

The texts follow the language chosen when the project was created and are rendered at
generation time. There is **no internationalisation library**: it would add a dependency, an
indirection and two catalogues to maintain in a base whose owner's first move will be to
rewrite the texts. Rewriting them is editing the files.

Embedding the build into the Rust binary is out of scope: it would make `cargo build` depend
on a prior npm build. Keeping the vendored components up to date is a recurring maintenance
task, not a mechanism — the theme is inlined by hand precisely so that installing depends on
no third-party generator.
