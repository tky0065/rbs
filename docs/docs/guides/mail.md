# Mail

`rbs add mail` installs SMTP sending into an existing project: five files under
`src/mail/`, a template directory, and a `Mailer` on your `AppState`. Like the other
bricks, it mounts no route — when a message goes out is a decision only your domain can
make.

Every snippet on this page is taken from
[`examples/file-drop`](https://github.com/tky0065/rbs/tree/main/examples/file-drop), a
project generated by the CLI and compiled in CI. Nothing here is written by hand for the
documentation.

## What gets installed

```text
$ rbs add mail
mail : envoi de courriels par SMTP : transport partagé, gabarits minijinja

plan pour /private/tmp/rbs-demo/depot

  + src/mail/mod.rs                 créé
  + src/mail/config.rs              créé
  + src/mail/template.rs            créé
  + src/mail/service.rs             créé
  + src/mail/tests.rs               créé
  + templates/mail/bienvenue.html   créé
  ~ src/main.rs                     modifié
  ~ src/state.rs                    modifié
  ~ Cargo.toml                      modifié
  ~ config/default.toml             modifié
  ~ .env.example                    modifié

  11 fichiers à écrire
✓ mail installée — 6 fichiers

  réglez [mail] dans config/default.toml — un SMTP local par défaut
```

A sample template, `templates/mail/bienvenue.html`, comes with it — a working starting
point you are meant to replace.

## Configuration

```rust file=examples/file-drop/src/mail/config.rs
```

The defaults describe a development server: port 1025 in the clear, which is what
[Mailpit](https://mailpit.axllent.org) and MailHog listen on. Production means
`tls = "starttls"` on port 587, or `tls = "wrapper"` on port 465, and an `smtp_user`.

**The password is the one value no versioned file carries.** `rbs add mail` writes
`RBS_MAIL__SMTP_PASSWORD=` into `.env.example` and nothing else — `config/default.toml` is
committed, and a password committed alongside it is a password to rotate.
[`rbs doctor`](../cli/doctor.md) reports the couple, not the variable alone:

```text
  ✗ mail       RBS_MAIL__SMTP_PASSWORD n'est renseignée ni dans le .env ni dans l'environnement
      ajoutez au .env la ligne que mail y attend, vide tant que smtp_user l'est :
      RBS_MAIL__SMTP_PASSWORD=
```

An empty password is legitimate as long as `smtp_user` is empty too: an unauthenticated
local relay needs neither.

## The transport

```rust file=examples/file-drop/src/mail/service.rs region=construction
```

Two things are decided here, and both are about *when* failure happens.

The builder is fallible but synchronous: no socket is opened, the first connection waits
for the first message. That is what keeps `AppState::new` synchronous, as with the
[cache](./cache.md).

The sender address, on the other hand, is parsed **now**. A typo in `from` stops the
project at startup rather than at the first send — the one moment where nobody is watching
the logs. Note the requirement in the doc comment: build it from inside a Tokio runtime,
because `lettre`'s pool registers a maintenance task as it is created.

The transport is built once and cloned with the state. `lettre` holds its own connection
pool, which a per-message transport would make pointless.

## Templates

Bodies are [minijinja](https://docs.rs/minijinja) templates read from the directory named
by `templates` — `templates/mail` by default:

```html file=examples/file-drop/templates/mail/depot.html
```

`Templates` wraps the environment in an `Arc`, because `AppState` is cloned on every
request and the templates should be loaded once rather than once per call. It uses
minijinja's `path_loader`, which refuses an absolute or upward-climbing name: a template
name coming from user input cannot escape the directory.

When a template is missing, the error names the full path — `templates/mail/absent.html` —
rather than the bare `absent.html` minijinja knows about, because a name alone points at no
directory when you are trying to find out what went wrong.

## Sending

The common case renders and sends in one call:

```rust file=examples/file-drop/src/mail/service.rs region=send_template
```

`message()` is available when you would rather build the `Message` yourself, and `send()`
takes one. Bodies are sent as `text/html`.

Transport failures come back as `Error::Internal`: a broken relay is a server-side fact,
and it tells the client nothing it could act on. It goes to the log, and the client gets
a 500 — see the [errors guide](./errors.md).

## Not making the client wait

Sending inside a handler makes the HTTP response wait for the SMTP server. When the
message does not condition the response, it can be detached instead:

```rust file=examples/file-drop/src/mail/service.rs region=send_detached
```

**Read the trade-off before reaching for it.** There is no queue and no retry: a message
lost is lost, and the log is the only trace. That is the price of a send that does not
hold the response, and it is a fair price for a notification — not for a password reset,
where the user is waiting for that mail and nothing else will tell them it failed.

## What the example does with it

`file-drop` mails the depositor when an upload is created, and does it in its own task:

```rust file=examples/file-drop/src/uploads/service.rs region=notify
```

The `owner_email` field is what makes the recipient come from the model rather than from a
constant — and, ending in `_email`, it earned the generated DTO its email constraint
without a line being written. See [`rbs generate`](../cli/generate.md).

Note that this is not `send_detached`: the message does not exist yet, since rendering the
template is itself part of the work being detached. The pattern is the same, one level up.

## Testing

The generated `src/mail/tests.rs` needs no server for six of its seven tests: the three
encryption modes each build a transport, an invalid sender is rejected by name, a built
message carries its sender and recipient, a template renders its variables, and a missing
template names its file without panicking.

The sixth earns a look. `send_detached` is proven against a fake server that accepts the
connection and never answers, so `lettre` stays hung on the SMTP banner: an awaited send
would block the test outright. Two assertions together — the call returns, and the
connection is nevertheless made — say what an empty method body could not.

The seventh is `#[ignore]`d and goes out to the SMTP server of the `[mail]` section —
Mailpit or MailHog in development. `cargo test -- --ignored` runs it, and
`RBS_MAIL__SMTP_PORT` overrides the port. See the [testing guide](./testing.md).

## What it leaves to you

- **when to send** — no route, no hook, no event. The example sends on creation because
  that is what its domain is about;
- **queueing and retries** — neither is here. A message that fails is logged and gone;
- **plain-text alternatives and attachments** — bodies go out as HTML;
  `lettre::Message` builds multipart if you need it;
- **bounce handling, unsubscribe links, per-locale templates** — not in this feature;
- **rate limits** — a provider that throttles will surface as transport errors, and
  nothing here backs off.

The code is in your tree, with no banner telling you not to touch it.
