# Seeds

Every project created by `rbs new` carries `src/seeds/`, a second binary whose only job is
to insert demonstration data. [`rbs seed`](../cli/seed.md) runs it.

Every snippet on this page is taken from
[`examples/newsletter-queue`](https://github.com/tky0065/rbs/tree/main/examples/newsletter-queue),
a project generated by the CLI and compiled in CI. Nothing here is written by hand for the
documentation.

## Typed Rust, not SQL

A seed goes through the entity your migration produced:

```rust file=examples/newsletter-queue/src/seeds/subscribers.rs region=seed
```

A renamed column breaks this at compile time. A `.sql` file of `INSERT` statements would
break in silence at run time, on the day someone runs it — which is the day you least want
to find out.

`id`, `created_at` and `updated_at` come from the column defaults, so `..Default::default()`
is what you write instead of choosing them. That single spelling matters beyond
convenience: it is the one write path per entity, and it is where the v7 identifier is
minted.

Note the `use newsletter_queue::subscribers::model;`. The seeds binary is a crate root of
its own, separate from the application's, so it cannot reach the entity through a module
tree it does not share — it reaches it through the project's library instead, the same one
`src/main.rs` builds on.

## The anchor

```rust file=examples/newsletter-queue/src/seeds/main.rs region=ancre
```

`rbs generate crud` writes the seed file and adds its name here, in generation order —
which is also the order of the migrations, and the only order that stays correct on the day
one seed depends on another.

A `mod` that is not inline cannot be written inside a block, so declaring the modules and
chaining them happens in one gesture, at item level:

```rust file=examples/newsletter-queue/src/seeds/main.rs region=macro
```

That macro is why there is a single insertion point here rather than two. `migration/`,
which has no equivalent, needs two anchors for the same job.

Nothing stops you from adding a seed by hand: create the file, add its name between the
markers.

## Running them

```text
$ rbs seed
subscribers : inséré
✓ seeds insérés
```

One line per seed, in the order of the anchor, and a summary. On a project where no seed
has been declared yet:

```text
$ rbs seed
✓ aucun seed déclaré — rien à insérer
```

Exit code 0, and cargo is never started. A project with nothing to insert has not failed.

:::warning
`rbs seed` refuses to run under `RBS_ENV=production`:

```text
$ RBS_ENV=production rbs seed
erreur : RBS_ENV=production : les seeds sont des données de démonstration, et rbs refuse de les insérer en production — relancez avec --force si c'est bien ce que vous voulez
```

The refusal lives in the command, not in the generated code. A seed is meant to be edited,
and a guard you can delete by accident while rewriting the file around it is not a guard.
`--force` is the way through, and it has to be typed.
:::

## Where they run

The seeds binary reads `RBS_DATABASE__URL` and connects on its own — it does not go through
`AppState`, and it starts no server. It pings the database before the first seed, so an
unreachable database says so up front instead of halfway through an insert.

This also means seeds see your migrations and nothing else: no middleware, no validation,
no service layer. What they insert is what the database will accept.

## What they leave to you

- **idempotence** — running `rbs seed` twice inserts twice, and a unique constraint will
  say so the second time. Make the seed check first if you need to re-run it;
- **ordering across entities** — the anchor's order is generation order; a seed that needs
  another's rows must come after it, and moving the line is how you say so;
- **volume** — these are demonstration rows, inserted one at a time. A fixture set of
  100,000 rows wants a different tool;
- **production data** — that is what migrations are for, and the refusal above is there to
  keep the two apart.

The code is in your tree, with no banner telling you not to touch it.
