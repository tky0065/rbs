# Building a help desk

The other tutorials each add one feature to `demo`. This one starts from nothing and ends
with an application: a help desk where signed-in people open tickets and comment on them,
through an administration space the binary serves itself. On the way it assembles what the
other pages showed one at a time — `auth`, relations between tables, `frontend-admin`, the
typed client — and it shows the one thing none of them does: where generated code gets
edited, and why.

It is a new project, `help-desk`, rather than `demo`, which carries `articles` and has
neither `auth` nor a frontend. Every excerpt below is read from
[`examples/help-desk`](https://github.com/tky0065/rbs/tree/main/examples/help-desk), a
project generated by the same commands and compiled in CI.

## What you need

What [Setting up](./setup.md) asked for — Rust, `rbs`, Docker for PostgreSQL — plus
Node.js for the frontend, and a browser.

## 1. Create the project

```bash
rbs new help-desk --lang fr
cd help-desk
git add -A && git commit -q -m "projet neuf"
rbs add frontend-admin
```

`rbs new` initialises the repository without committing. The commit is not required
here — `add` only refuses uncommitted changes to files Git already tracks, and nothing is
tracked yet — but it gives every step that follows a clean base, so that `git diff` shows
exactly what each command wrote. The plan is long; its file lines are cut
below, and what stays is the head and the tail.

{/* rbs:transcript cmd="rbs add frontend-admin" setup="rbs new help-desk --yes --lang fr --database-url postgres://rbs:secret@localhost:5432/help_desk && git add -A && git -c user.email=rbs@example.com -c user.name=rbs commit -q -m init" dans="help-desk" extrait="oui" */}
```text
frontend-admin : le shell d'administration : connexion, jetons, garde de route et les deux stores de l'application
frontend-admin exige frontend, mail, rate-limit, auth : posée avec elle

plan pour …/help-desk

  + src/modules/frontend/mod.rs                                             créé
  + frontend/src/admin/vues/Demonstration.vue                               créé
  ~ AGENTS.md                                                               modifié

  175 à créer, 15 à modifier
✓ frontend-admin installée — 175 créés, 15 modifiés
```

One fragment asked for, five installed. The admin shell needs someone to be signed in, so
it pulls in `auth`; `auth` sends verification and reset links, so it pulls in `mail`, and
it throttles login attempts, so it pulls in `rate-limit`. The shell is a Vue 3 application
mounted under `/admin`, built on the base that `frontend` lays down. From here on the
project knows it has a frontend, and the next two commands take it into account.

## 2. Model the tickets

```bash
git add -A && git commit -q -m "frontend-admin installée"
rbs generate crud tickets \
  --fields "sujet:string,detail:text,statut:enum(ouvert,en_cours,resolu,ferme),priorite:enum(basse,normale,haute),auteur:references:users"
```

From here on the commits are required: `generate` refuses to write while tracked files
carry uncommitted changes, so every step on this page starts with one.

{/* rbs:transcript cmd="rbs generate crud tickets --fields sujet:string,detail:text,statut:enum(ouvert,en_cours,resolu,ferme),priorite:enum(basse,normale,haute),auteur:references:users" setup="rbs new help-desk --yes --lang fr --database-url postgres://rbs:secret@localhost:5432/help_desk && git add -A && git -c user.email=rbs@example.com -c user.name=rbs commit -q -m init && rbs add frontend-admin && git add -A && git -c user.email=rbs@example.com -c user.name=rbs commit -q -m init" dans="help-desk" extrait="oui" */}
```text
  + src/tickets/controller.rs                          créé
  + migration/src/m20260923_134225_create_tickets.rs   créé
  + frontend/src/admin/vues/Tickets.vue                créé
  ~ src/auth/model.rs                                  modifié
  ~ frontend/vite.config.ts                            modifié
  ~ frontend/src/admin/montage.ts                      modifié
  ~ frontend/src/admin/rail.ts                         modifié

  12 à créer, 10 à modifier

  la référence « auteur » est requise : ni le seed de tickets ni ses scénarios de création ne peuvent deviner vers quelle ligne pointer — le seed n'est pas engendré, et les tests s'arrêtent aux cas qui ne créent rien
✓ tickets générée — 12 créés, 10 modifiés
```

Three kinds of field, each chosen for what it gets for free:

- `statut` and `priorite` are **enumerations**. The database guards them with a `CHECK`,
  the Rust side with an enum, and the screen renders them as drop-down lists.
- `auteur:references:users` is a **reference** to a table the project already has — the
  accounts `auth` created. The CLI inventories the project's entities before reading
  anything you typed, which is why it knows `users` lives in `src/auth/model.rs` and
  writes the inverse relation there.
- The rest are plain columns.

The `frontend/` lines are new to this command: because the project carries
`frontend-admin`, it wrote a `Tickets.vue` screen, mounted it in the router and the side
rail, and told Vite's development server to forward `/tickets` to the binary.

The warning before the last line matters for later. A required reference is one no
generated test can fill in — it cannot know which account to point at — so the tests of
`tickets` stop at the cases that create nothing. Section 4 is where that gap closes.

## 3. Hang comments on them

A comment belongs to a ticket, so `commentaires` references `tickets`. The order of the
two commands is the order of the foreign key, and the CLI enforces it. Had you run the
second one before `tickets` existed, nothing would have been written:

{/* rbs:transcript cmd="rbs generate crud commentaires --fields corps:text,ticket:references:tickets:cascade,auteur:references:users --dry-run" setup="rbs new help-desk --yes --lang fr --database-url postgres://rbs:secret@localhost:5432/help_desk && git add -A && git -c user.email=rbs@example.com -c user.name=rbs commit -q -m init && rbs add frontend-admin && git add -A && git -c user.email=rbs@example.com -c user.name=rbs commit -q -m init" dans="help-desk" */}
```text
erreur : relation « ticket » — « tickets » est introuvable dans ce projet
        → entités connues : commentaires, one_time_tokens, refresh_tokens, users
```

In the right order:

```bash
git add -A && git commit -q -m "tickets"
rbs generate crud commentaires \
  --fields "corps:text,ticket:references:tickets:cascade,auteur:references:users"
git add -A && git commit -q -m "commentaires"
```

{/* rbs:transcript cmd="rbs generate crud commentaires --fields corps:text,ticket:references:tickets:cascade,auteur:references:users" setup="rbs new help-desk --yes --lang fr --database-url postgres://rbs:secret@localhost:5432/help_desk && git add -A && git -c user.email=rbs@example.com -c user.name=rbs commit -q -m init && rbs add frontend-admin && git add -A && git -c user.email=rbs@example.com -c user.name=rbs commit -q -m init && rbs generate crud tickets --fields sujet:string,detail:text,statut:enum(ouvert,en_cours,resolu,ferme),priorite:enum(basse,normale,haute),auteur:references:users && git add -A && git -c user.email=rbs@example.com -c user.name=rbs commit -q -m init" dans="help-desk" extrait="oui" */}
```text
  + migration/src/m20260923_134226_create_commentaires.rs   créé
  + frontend/src/admin/vues/Commentaires.vue                créé
  ~ src/tickets/model.rs                                    modifié

  12 à créer, 11 à modifier
✓ commentaires générée — 12 créés, 11 modifiés
```

`cascade` makes deleting a ticket take its comments with it. `auteur` has no policy, so
it gets the default, `Restrict`: an account that wrote something cannot be deleted out
from under its writing. `src/tickets/model.rs` shows up as modified because a ticket now
*has* comments, and SeaORM needs that side of the relation too. The two migrations were
born one second apart, which is what guarantees `tickets` is created before the table
that points at it.

## 4. Take the author from the token

Everything so far was generated, and it has a hole. As generated, creating a ticket reads
`auteur_id` from the request body. Any signed-in account can therefore open a ticket in
someone else's name, and the screen asks whoever fills in the form to paste an account's
UUID. The author is not something the caller should choose: it is the caller.

Three files change, one per layer, in the order a request crosses them. First, the input
types stop accepting the field, at creation and at update — an author is not rewritten
later. The response keeps it.

```rust file=examples/help-desk/src/tickets/dto.rs region=entree
```

The controller is the only layer that sees the token. `Identity` has already checked it
before the handler runs; `user_uuid()` reads the account it belongs to, and hands it down.

```rust file=examples/help-desk/src/tickets/controller.rs region=create
```

The service takes the author as a parameter and sets it, without knowing where it came
from. That is the one-way dependency this project is built on: the controller knows
about HTTP and tokens, the service knows about tickets, and neither reaches into the
other's business.

```rust file=examples/help-desk/src/tickets/service.rs region=create
```

`update` in the same file simply loses the three lines that copied `auteur_id` over.

Do the same to `commentaires` — its `dto.rs`, `controller.rs` and `service.rs` change the
same way. `ticket_id` stays in the body there: which ticket a comment belongs to is the
caller's choice to make, who wrote it is not.

Then commit, because the next command will not run on a dirty tree:

```bash
git add -A && git commit -q -m "l'auteur est lu dans le jeton"
```

## 5. Carry the change to the screen

The screens call the API through a typed client, and `frontend-admin` does not ship it:
it is generated from *your* project's OpenAPI document, and the screens — `Tickets.vue`
included — import it, so the frontend does not build until it exists. Generate it now that
the contract is settled:

```bash
rbs generate client --lang ts --out frontend/src/api
```

{/* rbs:transcript cmd="rbs generate client --lang ts --out frontend/src/api" setup="rbs new help-desk --yes --lang fr --database-url postgres://rbs:secret@localhost:5432/help_desk && git add -A && git -c user.email=rbs@example.com -c user.name=rbs commit -q -m init && rbs add frontend-admin && git add -A && git -c user.email=rbs@example.com -c user.name=rbs commit -q -m init && rbs generate crud tickets --fields sujet:string,detail:text,statut:enum(ouvert,en_cours,resolu,ferme),priorite:enum(basse,normale,haute),auteur:references:users && git add -A && git -c user.email=rbs@example.com -c user.name=rbs commit -q -m init && rbs generate crud commentaires --fields corps:text,ticket:references:tickets:cascade,auteur:references:users && git add -A && git -c user.email=rbs@example.com -c user.name=rbs commit -q -m init" dans="help-desk" */}
```text
plan pour …/help-desk

  + frontend/src/api/client.ts   créé

  1 à créer
✓ client engendré — frontend/src/api/client.ts porte 29 opérations
```

`CreateTicket` in `client.ts` has no `auteur_id`: the client was read from the contract
as section 4 left it. You might expect the screen to fail type-checking, since it still sends that field. It does not: `npm run typecheck`
passes. The function that builds the request body has no declared return type, so
TypeScript does not check it for extra properties, and the server silently drops a field
it does not know. The screen would keep showing an "Auteur id" input that nobody reads.

So edit it by hand. In `frontend/src/admin/vues/Tickets.vue`, remove `auteur_id` from the
`Formulaire` interface, from the blank form `VIERGE`, from `corps()` and `saisie()`, and
delete the form's `champ-auteur_id` block. Leave it in `Ligne`, `depuis()`, the column list
and the detail panel's `PROPRIETES` — the screen still shows who opened each ticket.

```ts file=examples/help-desk/frontend/src/admin/vues/Tickets.vue region=corps
```

`Commentaires.vue` gets the same treatment. The general point: the typed client follows
the contract, but a screen only notices a field has disappeared where it types what it
sends.

One limit is left as it is. In `Commentaires.vue`, `ticket_id` is still a text input
that expects a UUID. Replacing it with a list of tickets is ordinary Vue work, and
[Frontend](../guides/frontend.md) describes the screen you would be editing.

## 6. Run it

Start PostgreSQL and Mailpit, apply the three migrations — the accounts `auth` created,
then `tickets` and `commentaires` — and create the administrator account that
`add frontend-admin` described:

```bash
docker compose up -d
rbs migrate up
rbs seed
```

Then build the frontend and start the binary, which serves it:

```bash
cd frontend && npm install && npm run build && cd ..
cargo run
```

## Verify

Open [`http://127.0.0.1:8080/admin`](http://127.0.0.1:8080/admin) and sign in with
`ADMIN_EMAIL` and `ADMIN_PASSWORD` from your `.env`. The rail has two new entries,
**Tickets** and **Commentaires**. Open a ticket: the form asks for a subject, a detail, a
status and a priority, and no author. Once saved, the list shows your account's id in the
author column.

The same guarantee is pinned down by a test, which is the part that keeps holding after
you stop looking. It posts a ticket whose body names *another real account* — a made-up
id would be refused by the foreign key, and the test would pass without proving anything —
and requires the ticket to come back in the caller's name:

```rust file=examples/help-desk/src/tickets/tests/auteur.rs region=auteur
```

The example carries this file and a second test, which checks that a `PATCH` naming
someone else leaves the author in place. Both read the database, like every test that
creates a row, so they are `#[ignore]` by default:

```bash
cargo test -- --include-ignored
```

## What was installed

Five fragments, two tables, two screens and one client, all from the CLI; one edit by
hand, in two places. In
[`examples/help-desk`](https://github.com/tky0065/rbs/tree/main/examples/help-desk):

- `src/tickets/` and `src/commentaires/` — the two features, `controller → service →
  repository → model`, with the edit in `dto.rs`, `controller.rs` and `service.rs`.
- `src/tickets/tests/auteur.rs` — the two tests written by hand.
- `frontend/src/admin/vues/Tickets.vue` and `Commentaires.vue` — the screens, without an
  author input.
- `frontend/src/api/client.ts` — the typed client, generated after the edit.
