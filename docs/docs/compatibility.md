# Compatibility

rbs follows [semantic versioning](https://semver.org). Inside a major version, what worked
keeps working: write `rbs-core = "1"` in a manifest, upgrade, and your project still
compiles.

A promise of that kind is worth exactly what its boundaries are worth. rbs publishes two
crates and writes code into your own source tree, so "the API" is not one thing. It is
five, and three of them are deliberately left out. This page says which, and why.

## What the promise covers

| Scope | Covered | Why |
|---|---|---|
| The public API of `rbs-core` | **yes** | It is what a major version freezes: every item the crate exports, and every signature it carries. |
| The format of the anchors and of `[package.metadata.rbs]` | **yes** | A project generated by one version of the CLI has to stay readable by the next. |
| The code generated into your project | no | It is yours from the moment it is written; the CLI never reads it back. |
| The library target of `rbs-cli` | no | `rbs-cli` ships a binary; that its library is visible is a build detail, not an offer. |
| The empty `redis`, `mail` and `storage` features of `rbs-core` | no | They reserve a name and carry no code. |

Both crates are published from one workspace and share a version number. A CLI that prints
`rbs 1.2.0` is the CLI that goes with `rbs-core 1.2.0`.

## The public API of the core

Everything `rbs-core` exports is covered: the `Error` type and its variants, the
application state, the middlewares, the configuration loader, the pagination and OpenAPI
helpers, and the items the `auth` feature adds. Inside 1.x none of them disappears, changes
signature, or changes meaning.

The freeze is measured rather than declared. `cargo-semver-checks` runs in CI on every
commit, comparing the working tree against the last version published on crates.io, with
every feature enabled — a removed variant or a renamed function fails the build and names
the item it lost. A page can be wrong about a freeze; a build cannot.

Two consequences are worth knowing before you write code against the crate:

- **Public enums and structs are `#[non_exhaustive]`.** Matching on `Error` needs a `_ =>`
  arm, and these types are built through their constructors rather than as literals. That
  is what lets a minor version add a variant without breaking anyone, and it is why the
  attribute was placed before 1.0 rather than after — after, it would have cost a major.
- **Adding is allowed, removing is not.** A minor version may bring new items, new
  variants, new fields. Code written to assume a list is complete will meet one that is
  longer.

Three types are exceptions, and stay exhaustive because generated code builds or
destructures them: the JWT claims, the validating JSON extractor, and the OpenAPI response
modifier. Their shape is frozen more tightly than the rest, not less.

## Anchors and project metadata

This is the scope one forgets, and the one whose loss hurts most.

Alongside your code, a generated project carries two things you never call: ten comment
anchors — nine Rust ones, `// <rbs:features>`, `// <rbs:routes>`, `// <rbs:openapi>`,
`// <rbs:migration_modules>`, `// <rbs:migrations>`, `// <rbs:state_champs>`,
`// <rbs:state_init>`, `// <rbs:startup>`, `// <rbs:seeds>`, plus a YAML one in
`docker-compose.yml` for whatever project has one, `# <rbs:services>` — and a
`[package.metadata.rbs]` section in `Cargo.toml` recording the rbs version that generated
the project, the features installed in it, and the database it targets. Neither is a Rust
API. A compatibility promise written for Rust APIs alone would step straight over both.

`// <rbs:features>` is where the promise shows what it is for. It moved to `src/lib.rs`
once projects gained a library — the file two separate binaries, the app and its seeds,
both reach into — but a project generated before that library existed has none, and on it
the anchor stays exactly where it always lived, in `src/main.rs`. `rbs generate` and `rbs
doctor` resolve to whichever file the project actually has, so the move breaks nothing
generated under an earlier version: it is the promise holding, not an exception to it.

A model can also carry two anchors of its own once it has a relation —
`// <rbs:relations:table>`, inside its `Relation` enum, and `// <rbs:related:table>`
beside it — the table's name standing in for the fixed name the ten above have, since a
file can hold more than one entity. They sit outside the count of ten because which file
carries them depends on the project's own features, not on the skeleton every project
shares; their comment syntax and their naming convention are frozen exactly the same way.

It must not, because they are the whole channel through which a later CLI recognises a
project an earlier one created. [`rbs add`](./cli/add.md) reads `[package.metadata.rbs]` to
know what is already installed, which is what makes it idempotent;
[`rbs generate`](./cli/generate.md) finds the anchors to know where a route, a module or a
migration goes; `rbs upgrade` rewrites the version recorded there. Rename an anchor, move
the section, change what a key means, and every project generated before that change stops
being a project the tools understand. The failure is silent in the worst way: nothing
crashes, the command simply finds nowhere to insert and prints a block for you to paste by
hand — on every command, forever.

So the format is covered exactly as the Rust API is. Inside 1.x:

- the ten anchor names and their comment syntax do not change, and neither does the rule
  that a command writes nothing when its anchor is missing;
- the keys of `[package.metadata.rbs]` keep their name and their meaning. A key may be
  added; an absent key reads as a default, never as an error.

What this does not promise is that a project generated in 0.4.0 already carries every
anchor a later feature wants. It does not, and it never will — new features bring new
anchors. That case is designed for rather than broken by: the command reports the anchor it
could not find and prints the block, and [`rbs doctor`](./cli/doctor.md) checks all ten —
nine on a project with no compose to carry the tenth — before anything goes wrong.

## What the promise leaves out

**The code generated into your project.** It is yours from the moment `rbs generate` writes
it. Nothing in it is marked "generated, do not edit", because [the whole
design](./architecture.md) is that you read and change it. rbs cannot promise the shape of
a file you have since rewritten, and it does not need to: no rbs release will ever rewrite
it either. `rbs upgrade` edits `Cargo.toml` and nothing else. If a later version generates
a different service layer, that is a difference between two new projects, not a change to
yours.

**The library target of `rbs-cli`.** The package exists to install the `rbs` binary. Its
library is visible because that is how the crate is built and tested, not because it is
offered as an API. Depend on it and a patch release may break you.

**The empty `redis`, `mail` and `storage` features of `rbs-core`.** They reserve names for
work that happens in your project rather than in the core, and carry no code. Enabling one
changes nothing today. The day one starts carrying code, that is an addition — and the
shape it takes is not promised in advance.

## Reading a version number

- **Patch** — 1.0.0 to 1.0.1: fixes. Nothing in a covered scope changes.
- **Minor** — 1.0 to 1.1: additions. New commands, new generated features, new items in the
  core, possibly new anchors in newly generated projects. Existing projects keep working.
- **Major** — 1 to 2: a covered scope may break. It comes with migration notes, which
  `rbs upgrade` prints for the jump it performs.

Pin what matches your appetite: `rbs-core = "1"` to take minor releases as they come,
`rbs-core = "1.2"` to take only patches. The changelog says what each release did; this
page says what it was allowed to do.
