# `rbs upgrade`

Aligns a generated project on the version of the CLI that runs it: the `rbs-core`
dependency and the version recorded in `[package.metadata.rbs]`. It then prints the
migration notes the jump crosses.

It writes to `Cargo.toml`, and to the two reserved zones of [`AGENTS.md`](../guides/agents.md)
— nothing else. The rest of the project — controllers, configuration, migrations, and
everything you write outside those two zones — is yours from the moment
[`rbs new`](./new.md) put it there, and re-rendering it on a newer version would erase your
work without you having asked for it by name. The guide is different: it is text rbs
produces and versions, so an upgraded project has to receive the handbook for the version
it now runs, rather than keep reading one written for the version it left behind.

:::note
rbs speaks French in its help screens and in its output. Every terminal block on this page
is verbatim, captured by running the command; only the prose around it is translated.
:::

## Synopsis

```text
$ rbs upgrade --help
Aligne le manifeste du projet sur la version du CLI : rbs-core et les métadonnées

Usage: rbs upgrade [OPTIONS]

Options:
      --force                  Met à niveau même si le working tree Git est sale
      --template-dir <CHEMIN>  Répertoire de templates remplaçant celles embarquées dans le binaire
  -y, --yes                    Prend les valeurs par défaut sans rien demander : le CLI reste scriptable
  -h, --help                   Print help
  -V, --version                Print version
```

`--force` is the only flag of its own. The two global options are accepted because clap
propagates them, and neither does anything here.

## A jump that carries a note

A project generated by rbs 0.4.0, upgraded by a 1.0.0 CLI:

```text
$ rbs upgrade
rbs 0.4.0 → 1.0.0

plan pour /private/tmp/rbs-demo/demo

  ~ Cargo.toml   modifié

  1 fichier à écrire
✓ manifeste aligné sur rbs 1.0.0

# rbs 1.0.0 — la surface publique du noyau est gelée

22 types de `rbs-core` portent désormais `#[non_exhaustive]` : les 7 enums (`Error`,
`ConfigError`, `JwtError`, `LogError`, `Status`, `Check`, `LogFormat`) et 15 structs —
les 5 de la configuration, plus `ProblemDetails`, `Health`, `Checks`, `CoreState`,
`ConnectError`, `Identity`, `Pagination`, `Page<T>`, `JsonFormat` et `PrettyFormat`.

Deux choses cessent donc de compiler dans votre code :

- un `match` exhaustif sur un de ces enums réclame un bras `_ =>` ;
- une de ces structs construite par un littéral hors du noyau ne l'est plus : passez par
  son constructeur (`Page::new`) ou par la configuration désérialisée.

`Claims`, `ValidatedJson<T>` et `CommonResponses` en sont exclus, et c'est délibéré : le
code qu'`rbs new` et `rbs generate` écrivent les construit ou les déstructure. Un projet
engendré traverse la version sans une ligne à changer.

  cargo update -p rbs-core, puis cargo test
```

Exit status 0. Four things happen there, in that order: the jump is named, the plan is
shown before a byte is written, the manifest is aligned, and the note of every version the
jump crosses is printed.

A note belongs to the version that introduces it, not to a pair of versions. An upgrade
that steps over several versions prints them all — otherwise the break brought by an
intermediate version would vanish for the sole reason that you did not stop there. A
project already past a note never sees it again.

The last line is not decoration. The manifest only states the version you want; until the
lockfile has followed, the project still compiles against the old core.

## The manifest, and the AGENTS.md zones

Immediately after the upgrade above, in the same project:

```text
$ git diff --name-only
AGENTS.md
Cargo.toml
```

Two files, and it is what makes the promise of [the compatibility
page](../compatibility.md) checkable by hand:

```text
$ git diff -U1 Cargo.toml
diff --git a/Cargo.toml b/Cargo.toml
index 5fd2f9c..7cf0dc8 100644
--- a/Cargo.toml
+++ b/Cargo.toml
@@ -12,3 +12,3 @@ default-run = "demo"
 [package.metadata.rbs]
-version = "0.4.0"
+version = "1.0.0"
 features = ["health"]
@@ -25,3 +25,3 @@ path = "src/seeds/main.rs"
 [dependencies]
-rbs-core = { version = "0.4.0", default-features = false, features = ["postgres"] }
+rbs-core = { version = "1.0.0", default-features = false, features = ["postgres"] }
 anyhow = "1.0"
```

Two lines: the record and the dependency. A core taken from a local path, through
`rbs new --core-path` — the mode rbs is developed in — keeps its path, since a path
dependency has no version to raise; only the recorded version moves.

```text
$ git diff -U2 AGENTS.md
diff --git a/AGENTS.md b/AGENTS.md
index 9064e97..77cfedc 100644
--- a/AGENTS.md
+++ b/AGENTS.md
@@ -1,6 +1,6 @@
 # demo — agent handbook

-<!-- rbs:guide 0.4.0 -->
+<!-- rbs:guide 1.0.0 -->
 ## CLI first

 This project is generated by rbs. **Anything rbs covers goes through the CLI**, never
```

Only the version on the opening marker moves here — the guide's own text changes only when
a version actually rewords it. The inventory zone underneath is recomputed too, on every
upgrade, but produces no diff of its own unless the project's fragments, entities or
database engine changed since the last time something wrote it: regenerating identical
content is not a byte written.

Whatever you added outside the two zones — the title, `## Project notes`, anything of your
own — is untouched, the same way the rest of the project is. [`rbs doctor`](./doctor.md)'s
`agents` check is what would have caught a stale guide before this upgrade ran.

The write goes through the same journal as every other command that touches an existing
project: should a write fail halfway, what was already written is undone.

## A jump that crosses no note

Not every version breaks something. A jump that crosses no note says so rather than
staying silent — a blank where a note was expected reads like a failure:

```text
$ rbs upgrade
rbs 0.3.0 → 0.4.0

plan pour /private/tmp/rbs-demo/demo

  ~ Cargo.toml   modifié

  1 fichier à écrire
✓ manifeste aligné sur rbs 0.4.0

  aucune note de migration pour rbs 0.3.0 → 0.4.0

  cargo update -p rbs-core, puis cargo test
```

Exit status 0.

## Nothing to do

Run it a second time on the same project and it stops before the plan:

```text
$ rbs upgrade
✓ le projet est déjà en rbs 0.4.0 — rien à faire
```

Exit status 0, and not a byte written — not even a rewrite of `Cargo.toml` to the same
content. The command is safe to put in a script that runs it on every checkout.

This is also why the Git guard comes after the plan rather than before it: a project that
has nothing to write has nothing to protect, and must be able to answer "nothing to do"
from a working tree full of your work in progress.

## A project ahead of the CLI

```text
$ rbs upgrade
erreur : le projet est en rbs 1.0.0, le CLI en 0.4.0 : `rbs upgrade` ne redescend pas un projet — relancez-le avec un CLI en 1.0.0 ou plus récent
```

Exit status 1. `rbs upgrade` never takes a project backwards. The usual cause is two CLIs
installed side by side — a `cargo install` and a `cargo run` in a clone — which is why the
message names both numbers: that is the only way to know which of the two you just ran.

A version number that does not reduce to three numbers is not held to be later. Upgrading
a manifest one cannot read is the lesser error of the two.

## A dirty working tree

```text
$ rbs upgrade
erreur : le working tree n'est pas propre : src/main.rs, src/router.rs — commitez, ou relancez avec --force
```

Exit status 1. An upgrade that has something to write wants a clean tree, so that the line
it changes stays distinguishable from yours in the next `git diff`. Commit, or pass
`--force` to upgrade anyway. Only tracked files count, and at most five are named before
the message says how many others there are — a tree with hundreds of changes would drown
the message in what it is meant to make readable.

Outside a Git repository the guard finds nothing modified and lets the upgrade through:
there is no history for it to protect.

## After the upgrade

`rbs upgrade` stops at the manifest, and its last line names the two commands that finish
the job: `cargo update -p rbs-core`, then `cargo test`. The first makes the lockfile follow
the version you have just asked for, the second tells you whether the notes above concern
your code.

Then [`rbs doctor`](./doctor.md), whose `versions` check compares the recorded version, the
`rbs-core` dependency and the CLI running the diagnosis — the three numbers this command
has just aligned.
